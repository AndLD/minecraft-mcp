# Opening ordinary doors

**Depends on:** [Tasks](../core/tasks.md).  
**Used by:** [Iron doors and switches](iron-doors-and-switches.md), [Animal farming](../farming/animal-farming.md) (optional).

- **Spiked, then dropped.** `mineflayer-pathfinder`'s own `canOpenDoors` movement option was tried first, as the plan called for: turned on in `mineflayer-bot-factory.ts` and run against a real closed door in Docker four times in a row. It never found a path at all (`no_path`, instantly, the bot never even moving toward the door), matching its own source comment ("Causes issues. Probably due to none paper servers."). Reverted to `false` (the default); doors are handled by a wrapper around `Navigator` instead, as the plan's fallback said.
- **`DoorOpeningNavigator`** (`src/skills/movement/door-opening-navigator.ts`) implements `Navigator` and wraps the real one (`MineflayerNavigator`): every skill that walks gets doors for free just by using the app's one shared `navigator` instance (`goto`, `follow_player`, and — since `PlanExecutor` also takes a `Navigator` for standing spots — building and excavating too), with **no change to `GoToSkill`, `FollowPlayerSkill`, or any other caller**.
- **How a trip is retried.** `goToPosition`/`goToPlayer` run the inner navigator; on `unreachable` or `stuck`, `BlockScanner.findBlocks` looks for the nearest closed door-like block **within `SEARCH_RADIUS` (16) of the bot's own position** (the port has no "search near this other point" of its own — the same limit `WallTarget`/`MarkerFinder` already live with), opens it, and retries the same trip — up to `MAX_DOORS_PER_TRIP` (3) different doors, each already-tried position excluded from the next search, so a door that turns out not to be the real blocker does not get opened again and again. Any other failure reason (`timeout`, `target_not_found`, ...) passes straight through untouched. An iron door or trapdoor found this way is never clicked: the trip fails with `needs_switch` instead (a later phase presses buttons and levers). A door that will not read the wanted state after `MAX_TRIES_PER_DOOR` (2) right-clicks fails the trip with `door_stuck`.
- **Close behind.** Once a trip succeeds, every door the wrapper itself opened during it (not ones already open) is right-clicked again, unless `NavigationOptions.closeDoors` is `false` (new field on the port, default true; the `goto` tool exposes it as `close_doors`, threaded through `GoToInput`/`NavigationOptions`). A door that will not close again is only logged (`Logger.warn`), not surfaced as a tool failure — the trip itself already succeeded.
- **`DoorAccess`** (`src/core/door.port.ts`) is the small port this needed: `stateAt(position)` (name + open, from `Block.getProperties()`, undefined when not loaded) and `toggle(position, signal)` (right-click, via the new `BotLike.activateBlock`). `classifyDoor`/`isOpenableByHand` (`src/skills/movement/door-table.ts`) are a pure table: any `*_door` (except `iron_door`), `*_fence_gate`, or `*_trapdoor` (except `iron_trapdoor`) is openable by hand; `iron_door`/`iron_trapdoor` classify as `'iron'` (needs a switch, not handled here) rather than being invisible to the finder — this is what lets the wrapper tell "no door nearby, genuinely unreachable" apart from "an iron one is right there."
- **`follow_player` gets door-*opening* for free** (the same wrapped `navigator`) but **not retry-on-stuck**: `NavigationRunner.run()` only does stuck detection when a fixed `goal` is given, and `follow()`'s call to it never sets one (a following goal moves), so a `follow` trip never actually produces a `stuck`/`unreachable` result for the wrapper to react to today. Scoped down deliberately rather than changing `NavigationRunner`'s stuck detection for a dynamic goal (real risk of regressing tunnel/mine hazard-chain behaviour, which relies on the exact same "give up" path) — the spec's own e2e list only ever exercises `goto`. `follow`'s door handling is a follow-up, not built here.
- **Not built, per the plan:** iron doors and switches (buttons, levers, plates) are Phase 17 (`feature/switches`); `needs_switch` is already wired through as the reason `goto` reports today, ready for that phase to answer it instead of leaving it to the agent.
- **Tests:** unit for `classifyDoor`/`isOpenableByHand` (every kind, iron excluded, everything else undefined), `MineflayerDoorAccess` (state read, default closed, toggle-and-confirm, `not_connected`, `out_of_reach`, a thrown activation wrapped as `failed`), `DoorOpeningNavigator` (opens and retries to success, closes behind, `closeDoors: false` leaves it open, `needs_switch` for iron without trying it, `door_stuck` after two failed tries, an unrelated failure or reason passed through untouched, trying a second nearest door when the first does not clear the way, giving up within the trip limit, the same behaviour for a player-target trip, following passes straight through, a failed close is logged not failed); integration through the MCP server on a stateful fake bot (`h.bot.pathfinder.failWith('NoPath')` simulates the closed-door failure, `h.bot.activateBlockCalls` and the block's `getProperties()` state confirm open-retry-close, `close_doors: false`, `needs_switch` for an iron door); e2e (`test/e2e/movement-perception/door-opening.e2e.test.ts`) walking into and back out of a real sealed house through a closed oak door with the door closed after each pass, `close_doors: false` leaving it open, a fence-gate pen closing behind the bot, and an iron door reporting `needs_switch` without being touched.
- **Closing on every path** (`feature/closing-doors-behind`, from a live session in which the bot left a chicken pen's gate open and the chickens walked out). The rule: **after passing through a gate, door, or trapdoor it opened, the bot closes it, whatever way the trip ended.**
  - `DoorOpeningNavigator.withDoors` closes what it opened in a `finally`: after an arrival, a failure, a cancel by `stop` or a reflex, and a thrown error. Closing is never cancelled by the stop (the click uses a signal that is never aborted), but a cancelled trip does not walk anywhere to do it: the bot must stay where the stop put it (a reflex may be making it run away). Levers pressed for an iron door are restored the same way.
  - A door is now approached before it is opened, and before it is closed: a click from where the bot stands is tried first; when the door does not change (the bot ended out of reach, for example at the far end of a pen it was sent into), the bot walks up to within 2 blocks and clicks again (`toggleWithApproach`). Before this, a trip to the far end of a pen failed with `door_stuck`, because the closest the pathfinder gets to an unreachable target is the far wall; the e2e test for this feature found it.
  - **Session list.** A door that could not be closed (too far and the trip was stopped, or it did not respond) is remembered (`leftovers()`). The next trip closes it first, `follow_player` closes it before it starts following, and `closeLeftovers(signal)` does it on request and returns those still open. A door opened with `close_doors: false` is left on purpose and is not remembered.
  - **Decision: a door found open is not closed by the navigator.** A player may hold a door open on purpose (for animals, for example), and a trip cannot tell "found open, passed through" from "was open, not used". Pens are different, so `PenGateGuard` (below) shuts an open gate of a pen the bot worked in.
  - **`PenGateGuard`** (`src/skills/farming/pen-gate-guard.ts`): at the end of `lure_animals`, `breed_animals`, `collect_eggs`, and the pen part of `tend_farm` (which also covers a cull walking in and out), on every outcome, it looks for fence gates in and one cell around the pen's bounds and closes each open one (walking up when needed, unless the task was stopped). A gate that stays open is reported: `gateLeftOpen` in the output of those tools, and in the pen's `problem` for `tend_farm`. `hunt_animals` inside a pen is not covered by the guard directly; the navigator still closes what it opened.
  - `MineflayerDoorAccess.toggle` now waits up to 8 ticks for the block to actually change instead of reading it back after 2: a late server answer used to look like "did not open", and the second click undid the first.
  - `follow_player` still never opens a door (its trips have no stuck retry, as before), so it has nothing to close; it only closes leftovers.
  - **Tests:** unit — the navigator closes after a failed trip, a cancel (without walking), a throw; walks back to close, and up to open; remembers a stuck door and closes it at the next trip, on request, and before following; leaves `close_doors: false` doors and doors found open alone; `PenGateGuard` (closes, ignores far gates, walks up, no walking after a stop, note on the result, failure passed through); the four pen skills each shut the gate and report one they could not; the door adapter waits for a late change. Integration — a pen gate left open is shut after `tend_farm` and after `breed_animals` through the tool layer. e2e (`door-opening.e2e.test.ts`) — a trip through a pen gate stopped in the middle of the pen ends with the gate shut, and a pen gate left open is shut when a breeding task in the pen ends.
