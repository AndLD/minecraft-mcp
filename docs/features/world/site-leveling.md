# Site leveling

**Depends on:** [Construction and building](construction-and-building.md).  
**Used by:** no other feature directly.

- **`FlattenAreaSkill`** (`flatten_area`/`preview_flatten`, `feature/site-leveling`, `src/skills/site-leveling/`) points the construction engine at a *surface* instead of a hole: cut what is above a target level, fill what is below it, clear what grows there. It is a client of `PlanExecutor` like `ExcavateSkill`/`BuildSkill`, not new engine code.
- **The area**, in priority order: `width`+`length` (a rectangle starting at `origin` — the player's own floored position by default — running `length` cells in `direction` and `width` to its right; `direction` defaults to the player's yaw snapped to the nearest cardinal via `directionFromYaw`/`rectangleFromFacing`, `src/skills/site-leveling/facing.ts`); otherwise two corner markers (below); otherwise `missing_area`/`markers_not_found`. `margin` grows the rectangle on every side afterwards.
- **Corner markers.** `MarkerFinder` (`src/skills/site-leveling/marker-finder.ts`) looks for two vertical, two-block-high stacks of `dirt`/`cobblestone` (or one, via `marker_block`): a candidate is a stack's own foot (the cell below is not the same block, so a natural column going deeper is never mistaken for one), on solid ground, with nothing solid above the stack or on any of the four sides at either height. It calls `BlockScanner.findBlocks` with a generous `count: 400`, not a handful: dirt and cobblestone are also ordinary terrain, so in a dirt-heavy area the nearest few dozen matches can all be buried ground, with the real marker stacks — a few blocks off in some other direction — never in the running (found while writing the e2e test). The search is centred on the bot, not the player, the same as every other `findBlocks`-based tool: the port has no "from position" of its own. Fewer than two candidates is `markers_not_found`; more than two takes the two nearest. The rectangle is their bounding box, corners included — **the markers themselves are part of the instruction, not obstacles**: they are cut away with the rest of the plot.
- **The level.** `here` (default: the block under the player's feet), an explicit `y`, `markers` (the lower of the two marker bases — looked up independently of whether markers were also used for the area), or `auto`. `auto` only **suggests** a level (`preview_flatten`'s `suggestion`: the survey's median height, next to the cost of using `here` for comparison) and `flatten_area` refuses it outright (`ambiguous_level`): the agent must preview first and pass an explicit `y`.
- **The height survey** (`src/skills/site-leveling/height-survey.ts`) scans every column of the rectangle from 30 blocks above to 30 below the player's own level (`SURVEY_REACH`, not the whole world column) for the topmost solid block, giving the median (for `auto`) and, per column, how deep a hole is for the fill pass.
- **Natural vs. player-made** (`src/skills/site-leveling/natural-terrain.ts`, pure tables): `isNaturalTerrain` (stone, soil, sand, ore, ...) cuts and counts as `cut`; `isVegetation` or, with `clear_trees`, a log or leaves (`isTreePart`) clears and counts as `cleared`; anything else is a player-made block, reported as `blocked_cells` and left alone unless `clear_structures` is true (then it is cut too). `pickFillBlock` picks the biggest pile of a real fill candidate (`dirt`, `cobblestone`, `sand`, `gravel`, ... — `FILL_CANDIDATES`) from what a cut gained, `dirt` otherwise.
- **Two passes, not one.** `buildCutPlan` (top down, so nothing falls on the bot) runs first through `PlanExecutor`; only once it has actually run does the skill know what the cut gained, pick `fillBlock` from it (or use an explicit one), and build `buildFillPlan` (bottom up; `surfaceBlock` only on the very top cell of each filled column) as a **second, separate** `PlanExecutor` run. A single combined plan would refuse up front with `missing_materials` for fill blocks the cut has not produced yet, since the executor checks what is carried once, before anything runs — splitting it is what makes "little or nothing needs fetching" true. A fill failure after a successful cut is reported with `detail.cutDone: true`.
- **Safety** is entirely the engine's own, reused unchanged: `hazards: 'refuse'` refuses `unsafe_site` up front for lava in or next to the plot's bounding box (`SiteSafety.hazards`), and `AreaGuard` refuses `protected_area`, both through the ordinary `PlanExecutor.preview()`/`.run()` checks — no new safety code for this feature. Holes deeper than `max_fill_depth` (default 6) are left alone (`too_deep`), never filled by accident.
- **Not built:** saving the plot as a landmark (`label`) — `set_landmark`/`list_landmarks` are Phase 22 (discovery) and do not exist yet; the result still reports `bounds`/`level` for `build`/`build_farm` to use directly.
- `EntityScanner`'s `player()` gained `yaw` (`PlayerInfo.yaw`, optional; `MineflayerEntityScanner` reads it from the player's own entity, the same radian convention `LookTarget` already uses) so facing can be read at all; this is the only port change the feature needed.
