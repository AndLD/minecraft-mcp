# Iron doors and switches

An iron door cannot be opened by hand (Phase 16 already classifies it as `'iron'` and refuses to click it). This phase finds the button, lever, or plate that opens one — by where it is, since the redstone wiring behind it is invisible — presses it, and does so only as far as the player's own standing rule allows.

- Branch: `feature/switches`. Reuses `DoorOpeningNavigator`, `DoorAccess`, and `classifyDoor` from Phase 16 unchanged; adds the equivalent pair for switches.
- **`SwitchAccess`** (`src/core/switch.port.ts`) mirrors `DoorAccess` exactly: `stateAt(position)` (name + `powered`, from `Block.getProperties()`) and `press(position, signal)` (right-click, via the same `BotLike.activateBlock` doors already use — its own doc comment already said "a button or lever is used this way too"). A pressure plate has no `press`: it is powered by an entity standing on it, so the way to "press" one is to walk onto it, not to click it. `classifySwitch` (`src/skills/movement/switch-table.ts`) is a pure table mirroring `door-table.ts`: `lever` by exact name, `*_button`, `*_pressure_plate` (including the weighted ones) by suffix.
- **`SwitchFinder`** (`src/skills/movement/switch-finder.ts`) lists buttons, levers, and plates within `SWITCH_SEARCH_RADIUS` (4) of a position (typically a door), nearest first. `BlockScanner.findBlocks` only searches from the bot's own position (the same limit `WallTarget`/`MarkerFinder`/`DoorOpeningNavigator` already live with), so the finder widens that bot-centred search by a margin and then filters and re-sorts by real distance to the position asked about — correct as long as the bot is already close enough to the target to have found it in the first place, which it always is here (a navigation retry only reaches this code once the bot is stuck right next to the door). **Not modelled: which side of the door a switch is on** — the plan's "on the side the bot is on" refinement was cut; a switch on the far side within radius still counts as a candidate. Ranking is by distance only.
- **`IronDoorOpener`** (`src/skills/movement/iron-door-opener.ts`) is the ranked-guess-and-verify loop: press the nearest candidate, read `DoorAccess.stateAt` on the door, and if it did not open, try the next — at most `MAX_CANDIDATES` (4) switches, over `MAX_ROUNDS` (2) passes, so a switch that needed a second try (a stale read) is not abandoned after the first round. Ends with `no_switches_found` (nothing nearby at all) or `door_did_not_open` (everything nearby was tried, listed in `tried`, and none of it worked). Pressing itself branches on kind: a button or lever is walked up to within `SWITCH_REACH` (3) and right-clicked (`SwitchAccess.press`); a plate is walked onto directly (`within: 0`) — standing there is what powers it. The `Navigator` `IronDoorOpener` walks with is a constructor dependency, not necessarily the app's wrapped one: see below.
- **`IronDoorHandler`** (`src/skills/movement/iron-door-handler.ts`) is what `DoorOpeningNavigator` calls when it finds a closed iron door, and applies the standing `SwitchPolicy` (`auto` default, `ask`, `never`; `src/state/switch-policy.ts`, `set_switch_policy` tool, mirrored into `StandingInstructions` like `FoodPolicy`): `auto` runs `IronDoorOpener` itself and, on success, tells `DoorOpeningNavigator` which switch was used so a lever can be put back later (a button or plate needs no such note: they release themselves); `never` fails the trip with `needs_switch` without even searching; `ask` searches and, if it finds candidates, fails with **`iron_door_blocked`** naming them (a new `NavigationFailureReason`, alongside `needs_switch` for when `ask` finds nothing nearby) so the agent can tell the player and then call `open_door` or `press_switch`. The default was flipped from the plan's own `ask` to `auto` shortly after this phase shipped, once live use showed that asking before every iron door was more friction than the caution was worth; `ask`/`never` remain for a player who wants to be consulted.
- **Restoring a lever, like closing a door, happens once the whole trip has gone through** — `DoorOpeningNavigator.withDoors` collects lever positions the same way it already collects opened wooden doors, and only presses them back (`IronDoorHandler.restoreLever`, gated by the same `closeDoors` option) after `attempt()` finally succeeds, never before: pressing it back earlier would close the door again while the bot is still walking through it.
- **Avoiding recursion.** `IronDoorOpener` needs a `Navigator` to walk to a candidate switch, but the one `DoorOpeningNavigator` hands to its own `IronDoorHandler` must not be the wrapped `navigator` itself (that would call back into the class that is still in the middle of handling this exact door). `app.ts` gives the internal, policy-driven opener the **raw** `rawNavigator` for this reason. The two standalone tools below (`open_door`, `press_switch`) are top-level call sites, not nested inside `DoorOpeningNavigator`, so they use the ordinary wrapped `navigator` and get ordinary wooden-door handling for free while walking to a switch.
- **Tools resolve "at, or the one the player is looking at" the same way `room`'s wall does** (`src/mcp/tools/resolve-target-position.ts`, a small free function in the tool layer, not a class — the lookup here is just "read the look, use its position," with no floor-scanning or fallback logic to justify `WallTarget`'s own class shape): `at` wins if given; otherwise `for_player` (or the configured owner) must be looking at something, or the tool fails before anything happens.
  - **`press_switch`** walks to a button, lever, or plate and presses it, reporting the nearest door within reach and whether it is now open. Fails `not_a_switch` for anything else at that position.
  - **`open_door`** opens a wooden or iron door, gate, or trapdoor **regardless of the switch policy** — calling this tool is itself the decision to try, the same way `resume_task` answering a paused hunt is the decision to keep going. A wooden one is right-clicked directly; an iron one goes through `IronDoorOpener`. `walk_through` (default true) then walks the bot to a point mirrored across the door from where it stood before the call (`doorPosition * 2 − botPosition`, the only way to say "the far side" without any notion of which way the door faces) so the door is not just opened but actually crossed; `restore` (default true) closes a wooden door again or presses a used lever back, once through — a button or plate needs nothing.
  - **`find_switches`** is read-only: `SwitchFinder.near`, nothing pressed.
  - **`set_switch_policy`** saves `SwitchOpenPolicy` the same way `set_food_policy` saves `LowFoodPolicy`: a tiny `ProfileScoped` state class plus a tool that also mirrors the non-default choice into `StandingInstructions`.
- **Timing is not simulated, only respected.** A stone button holds a door open for about a second, a wooden one 1.5 — there is no code here that waits out or extends that window; `IronDoorOpener` presses and `open_door` walks through immediately afterward with no pause in between, which is what makes the window survivable at all. This only works reliably when the switch is genuinely close to the door (as the e2e arena's is); a button several blocks away is a real, undocumented-elsewhere risk this phase does not solve.
- **A switch's own confirm wait is longer than a door's.** `MineflayerSwitchAccess.press` (`src/bot/mineflayer-switch-access.ts`) waits `CONFIRM_TICKS` (6, versus `MineflayerDoorAccess`'s 2) after the click before returning — found by an e2e run that pressed a lever, read the door's state one tick too early, saw it still closed, and pressed the same lever *again* (undoing the real success, since a false "it didn't work" retries by re-toggling the same switch). A caller of `press` almost always goes on to read some *other* block (the door the switch powers), one extra hop of redstone propagation away from the click itself, and needs the margin.
- **Not built, per the plan:** which side of the door a switch is on (see `SwitchFinder` above); a combined "one spot in reach of both the switch and the door" standing-spot chooser for tighter timing margins; buttons/plates counted or discovered for `find_switches` beyond the plain radius search.
- **Tests:**
  - unit: `classifySwitch` (every kind, doors excluded), `MineflayerSwitchAccess` (state read, default unpowered, press-and-confirm, `not_connected`, `out_of_reach`, a thrown activation wrapped as `failed`), `SwitchFinder` (ranking, ignoring anything past the radius, blocks that are not switches, no known switch names at all), `IronDoorOpener` (presses the nearest lever and confirms success, walks onto a plate instead of clicking it, tries the next candidate when the first does not open the door, `no_switches_found`, `door_did_not_open` after both rounds, the 4-candidate cap, stopping at once when aborted, `restoreLever`), `IronDoorHandler` (`never`/`ask`/`auto`, `ask` falling back to `needs_switch` with nothing nearby, `auto` naming a lever to restore but not a button, `auto` reporting `needs_switch` when the opener could not do it, delegating a restore), `DoorOpeningNavigator` (hands an iron door to `ironDoors` and retries on success, restores a lever only once the trip succeeds, skips the restore when `closeDoors` is false, passes an `ironDoors` failure straight through, still falls back to `needs_switch` when no handler is wired at all — unchanged from Phase 16), `PressSwitchSkill` and `OpenDoorSkill` (each action, `not_a_switch`/`not_a_door`, a navigation failure passed through, the mirrored walk-through point, a door already open needing no toggle, no restore after a button), the four tools' `at`-or-look resolution and resume arguments, `SetSwitchPolicyTool` (save, mirror, clear on `auto`, fails with no active world)
  - integration: `goto` through an iron door on a stateful fake bot extended with a `switchPowered` map and a `linkSwitch(switchPosition, doorPosition)` wiring table (the fake has no redstone simulation of its own, so a test links a switch to the door it opens by hand) — `iron_door_blocked` naming the lever found (policy `ask`, set explicitly), and (policy `auto`) pressing the linked lever, walking through, and restoring it, with `activateBlockCalls` showing exactly the lever's position pressed twice, never the door itself
  - e2e (`test/e2e/movement-perception/switches.e2e.test.ts`), against real redstone on a real Paper server, floor-mounted switches (simpler and just as real as a wall-mounted one, and load-bearing for the timing test): a lever opens an iron door, the bot walks through, and the lever is pressed back, closing the door again; `close_doors: false` leaves both the lever and the door as `auto` left them; a wooden button survives the walk-through before it times out on its own; `press_switch` and `open_door` (which works even with the policy set to `never`) exercised directly; `find_switches` lists the lever and touches nothing; policy `ask` (set explicitly, since it is no longer the default) reports `iron_door_blocked` naming the lever, untouched. **Gotcha found here, not simulated in fakes:** several houses are built across this one file's tests, 10 blocks apart; a plain "the bot sees N of this block name" wait (Phase 16's own pattern) can be satisfied by an *earlier* test's still-visible structure within the default 32-block search radius, racing ahead of the new one a given test actually needs — the fix waits for a block of that name at the *exact* position expected, not just a count.
- **Exit criteria:** "get into the house" through an iron door with a lever beside it finds it, presses it, walks in, and leaves the lever as it was, by itself (the default `auto` policy); a player who says "ask me first" (`set_switch_policy: ask`) instead gets the switches found reported, and waits to be told to use them; a switch that genuinely does nothing is reported as `door_did_not_open` with what was tried.
