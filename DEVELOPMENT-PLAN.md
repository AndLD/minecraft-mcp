# Development Plan

Goal: a Mineflayer-based MCP server so Claude can play survival Minecraft 1.21.1 with the user: gather, craft, build, discover structures, following in-game chat instructions. Architecture rules are in [AGENTS.md](AGENTS.md).

## Decisions (fixed)

| Topic | Decision |
|---|---|
| Language | TypeScript (strict), ESM, Node 22+ |
| Minecraft | 1.21.1 vanilla, LAN world from TLauncher, bot in offline auth |
| Transport | MCP over stdio, `@modelcontextprotocol/sdk` |
| Config | `.env`: `MC_HOST=localhost` (default), `MC_PORT` (optional: when empty the port is discovered from the LAN world broadcast), plus the variables listed in README. The `connect` tool can override host/port at runtime |
| Instruction channel | In-game chat → `ChatRouter` → `AgentInbox` → agent long-polls `wait_for_chat` |
| Real-time behavior | Static-code reflexes (eat, flee, lava, drowning, `stop`); the agent only issues high-level goals |
| Threat policy | Always flee from skeletons and creepers; always flee at low health; fight all other hostile mobs (zombies, spiders, etc.); ignore endermen. Encoded as a data table, see AGENTS.md |
| Block collection | Own `CollectBlocks` skill built on pathfinder behind the `Digger` port; `mineflayer-collectblock` is not used (can be swapped in later behind the same port) |
| Hunting | A dedicated hunting flow (not just reflex combat): find huntable animals, approach, kill with correct attack timing, collect drops, optionally cook and store the food. Tamed, named, and last-breeding-pair animals are protected by default. Low food is handled by a policy: ask by default, or hunt and cook when the user's instruction allows it |
| Item handover | The bot can give items to a player on request: fetch the items (inventory first, then remembered chests), walk to the player, drop them at a safe distance so they land at the player's feet, verify they were picked up, and retry or report. Large amounts can go into a chest instead. Reserve items (current tools, armor, food) are kept unless asked |
| Drop recovery | Automatic by default, skippable on the user's request. Covers the bot's own drops: its inventory after a death, and handed-over items nobody picked up. `auto` never wades into lava, void, or other hazards (it asks instead); the user can say "forget it" at any time, or set a standing instruction. Skipped drops are kept as records with coordinates and can be recovered later |
| Persistence | Everything worth remembering is saved per world profile through a `StateStore` (atomic JSON files under `DATA_DIR/<profile>/`): world knowledge, containers and rules, standing instructions, a task journal (interrupted tasks are offered for resume, never auto-resumed), an instruction/event log, and agent notes. On `connect` the bot returns a session briefing |
| World identity | Detected automatically first (fingerprint from signals the server exposes, such as the hashed seed, world name/MOTD, spawn point); if it cannot be determined or is ambiguous, fall back to a profile name given by the user (`WORLD_PROFILE` or `connect(profile)`) |
| Storage | Chests are first-class. The user can designate specific containers for specific kinds of items (rules); with no matching rule the bot uses any chest with room. Inventory-full handling is a policy: ask the user by default, or offload to storage and return when the user's instruction (per call, or a standing instruction for the session) allows it |
| Architecture | Ports and adapters, SOLID; Mineflayer isolated in `src/bot/` |
| Testing | Jest (`@jest/globals`, TypeScript, ESM). Three automated tiers: unit and integration (offline, fast, run by `npm test`) and e2e against a real headless Minecraft 1.21.1 server in Docker. E2E tests are organized per phase: during a phase only that phase's own e2e tests are run; the complete e2e suite runs once, after all primary phases. Manual in-game checks remain a per-phase human step |
| Testability | All code is testable by construction: dependencies injected via ports, `Clock` and `Random` injected, the app wiring lives in a `createApp()` factory, and Mineflayer sits behind thin adapters |
| Git workflow | Git Flow. `main` = production, `development` = integration. Every phase or feature lives in its own branch created from `development` |
| E2E environment | Docker: `itzg/minecraft-server` (Paper 1.21.1, `ONLINE_MODE=FALSE`, RCON enabled) started by Jest global setup via `testcontainers`; scenarios prepared and verified through RCON |
| Tooling | eslint, prettier, tsx (dev), tsc (build), Jest, testcontainers, rcon-client |

## Risks and how the plan addresses them

| Risk | Mitigation |
|---|---|
| LAN world may reject offline-mode bots | Phase 0 spike proves it first. Fallback: install a local Paper 1.21.1 server with `online-mode=false` (the code does not change, only the host/port) |
| Random LAN port every session | `connect` accepts host/port overrides; documented flow. If the spike shows the LAN broadcast is readable, the port can be discovered automatically |
| Coordinates from one world pollute another (LAN worlds have no stable address) | Per-world profiles. World fingerprint detected automatically; user-given name as fallback; mismatch warnings in the session briefing |
| Interrupted tasks resumed blindly after a relaunch | Task journal marks them `interrupted`; the agent asks the user before resuming |
| Corrupted or outdated state files | Atomic writes, backup copy, schema versions with migrations, fall back to an empty state with a warning |
| Agent latency (seconds per turn) | Coarse tools, autonomous tasks, reflexes in code, event log returned with chat |
| Tool calls time out on long work | Task model: bounded wait, then `running` + `get_task_status` / `cancel_task` |
| Structures are not queryable from the client | Physical exploration + signature detection on loaded chunks; optional `/locate` accelerator when the bot is opped |
| Building is fiddly (reach, placement faces, terrain) | Blueprint layer with layer-by-layer placement, scaffolding, verification pass, and retries |
| Pathfinder gets stuck | Stuck detection in `Navigator` adapter, timeouts, and clear failure reasons for the agent |
| Bot empties or fills the wrong chests | Explicit rules and labels, `protected` flag, reserve list for tools and food, action reports in chat, index refresh on mismatch |
| Griefing player builds | Protected landmarks; the digger refuses protected areas unless overridden |
| stdout pollution breaks the MCP protocol | Logger writes to stderr only; lint rule bans `console.log` |
| Jest with native ESM is fiddly (`--experimental-vm-modules`, `.js` import mapping) | Solved once in Phase 1 with a working config and a sample test before any feature code |
| Hunting wipes out animals or kills someone's pets | `AnimalCatalog` protection rules: never attack tamed animals, named animals, villagers and golems; keep a breeding pair per species in the area by default; user can override per call |
| Dropped items get lost (lava, void, despawn after 5 minutes, bot re-collects its own drop) | Safe drop spot check, drop from a distance and step back, verify pickup, chest mode for large amounts; unclaimed items and death drops are handled by the drop-recovery feature with a despawn deadline |
| Death loops (bot dies again while recovering its drop) | Hazard assessment before approaching, staged approach, max attempts (default 2), and asking the user when the spot is unsafe; the user can skip recovery at any time |
| Fakes drift from real Mineflayer behavior | Adapters are thin and unit-tested against a stub of the Mineflayer API; the Docker e2e suite (from the e2e-harness feature) runs the real bot against a real server; each phase still ends with a manual in-game check |
| E2E tests are slow and timing-sensitive | Small smoke-level suite (a handful of scenarios per phase), deterministic world (superflat or fixed seed), mobs and time controlled via RCON, generous timeouts, kept out of `npm test`; failures dump server and bot logs |
| E2E needs Docker and the server EULA | Documented prerequisite; the e2e scripts fail fast with a clear message when Docker is missing; EULA accepted through the container env |

## Phases

Each phase ends with working, tested software and a manual check in the game. Estimates are rough working-session counts.

Every phase (and any later feature) is developed in its own branch created from `development` (see [Git workflow](#git-workflow)). Every phase includes its own unit and integration tests, and from the e2e-harness feature onward also e2e scenarios for its user-facing behavior. While working on a phase, run **only that phase's own e2e tests** (not the ones from earlier phases); a phase is done when its unit, integration, and own e2e tests pass. The complete e2e suite is run once at the end (see the final gate in the hardening phase).

### Phase 0: Feasibility spike (½ session)

Branch: `feature/feasibility-spike`. Throwaway script (removed after the scaffold; it lives in git history), not part of the architecture and not covered by tests.

- Repository bootstrap first: initial commit with the docs on `main`, then create `development` from it.
- Bare Mineflayer bot joins the LAN world (1.21.1, offline) and echoes your chat back.
- Confirm: connection works, chat events arrive, bot can walk to you with `mineflayer-pathfinder`.
- Probe world-identity signals available to the client: hashed seed in the login packet, the server status/MOTD (world name), the LAN broadcast (which may also reveal the port automatically), world spawn point, dimension. Record which of them are stable across re-opening the same world.
- **Exit criteria:** the bot is visible in the world and replies to chat. If not, switch to the Paper fallback.

### Phase 1: Project scaffold (½ session)

- Branch: `feature/project-scaffold`.
- `package.json` (ESM, scripts), `tsconfig.json` (strict), eslint + prettier, Jest, `.gitignore`, `.env.example`.
- Jest setup: `jest.config.ts` for TypeScript + ESM (run through `node --experimental-vm-modules`), `.js`-extension module mapping, `@jest/globals` imports, separate unit and integration projects, coverage thresholds. Scripts: `test`, `test:unit`, `test:integration`, `test:coverage`.
- Test helpers: `test/fakes/` (fake `Clock`, `Random`, `Logger`) and a builder/factory convention for test data.
- `src/config/env.ts`: zod-validated env (`MC_HOST` default `localhost`, `MC_PORT`, `MC_VERSION`, `MC_USERNAME`, `MC_AUTH`, `MC_OWNER`, `MC_AUTO_CONNECT`, `DATA_DIR`, `LOG_LEVEL`).
- `Logger` port with a stderr implementation; lint rule against `console.log`.
- `CLAUDE.md` containing `@AGENTS.md` so Claude Code picks up the rules (already created).
- **Tests:**
  - unit: env schema (defaults, required `MC_PORT`, invalid values), stderr logger (never writes to stdout)
  - integration: `createApp()` with the config and fake ports builds without side effects
- **Exit criteria:** `typecheck`, `lint`, `test` pass on an empty-but-wired project; coverage gate is active.

### Phase 2: Core skeleton and MCP shell (1 session)

- `src/core`: port interfaces (`Connection`, `ChatPort`, `VitalsReader`, `Clock`, `Logger`) and shared types (`Position`, `Result`).
- `src/bot`: `MineflayerConnection` (connect/disconnect/reconnect events, error handling) and chat adapter.
- `src/chat`: `AgentInbox` (chat and events, `wait(timeout, signal)`, bounded buffer), `ChatRouter` (owner filtering, then fixed commands, then inbox), `StopCommand`.
- `src/bot`: `LanDiscovery` port and adapter (listens to the LAN broadcast on `224.0.2.60:4445`, returns the port and world name; used by `connect` when `MC_PORT` is not set).
- `src/mcp`: `ToolRegistry`, `ToolDefinition`, server bootstrap; tools `connect`, `disconnect`, `get_status`, `wait_for_chat`, `say`, `whisper`.
- Wiring in `src/app.ts` (`createApp(config, deps)`), so it can be built in tests with fakes; `src/index.ts` only reads env, calls `createApp`, and starts the stdio transport.
- Branch: `feature/core-mcp-shell`.
- **Tests:**
  - unit: `AgentInbox` (ordering, bounded buffer, owner filter, timeout, concurrent waiters), `ChatRouter`, `StopCommand`, `ToolRegistry`, each tool's input validation and output mapping, `MineflayerConnection` and chat adapter against a stub Mineflayer bot (event emitter)
  - integration: real MCP server and client connected through the SDK's in-memory transport, real `AgentInbox`/`ToolRegistry`, fake `Connection`/`ChatPort`: `connect` → incoming chat → `wait_for_chat` → `say`
- **Exit criteria:** register the server in Claude Code; Claude connects, says hello in game, and answers a chat message through the `wait_for_chat` loop.

### Phase 3: Movement and perception (1 session)

- Ports: `Navigator`, `BlockScanner`, `EntityScanner`. Adapters over pathfinder and Mineflayer.
- `Navigator` features: goto position/player/block, follow, stop, stuck detection, timeouts, safe movement profile (no digging through player builds, no lava).
- `TaskManager` (single active task, abort, progress, bounded wait) and `get_task_status` / `cancel_task`.
- Tools: `goto`, `follow_player`, `stop`, `look_around`, `find_blocks`, `get_nearby_entities`, `get_player_position`, `get_inventory`.
- Branch: `feature/movement-perception`.
- **Tests:**
  - unit: `TaskManager` (single active task, cancel, abort propagation, progress, timeout, bounded wait returning `running`), movement skills against a fake `Navigator` (success, unreachable, stuck, aborted), perception summaries against fake scanners
  - integration: chat "stop" → interceptor → `TaskManager` cancels a running fake-navigator task; `goto` over the wait budget returns `running`, then `get_task_status` reports completion (with a fake `Clock`)
- **Exit criteria:** "come here", "follow me", and "stop" work from in-game chat; a `goto` beyond the wait budget returns `running` and completes later.

### Phase 4: E2E test harness (1 session)

- Branch: `feature/e2e-harness`.
- `docker/` with the server configuration (image `itzg/minecraft-server`, `TYPE=PAPER`, `VERSION=1.21.1`, `ONLINE_MODE=FALSE`, `EULA=TRUE`, RCON on, superflat world, `SPAWN_PROTECTION=0`, `DIFFICULTY` and `doMobSpawning` set per suite).
- Jest `e2e` project with a global setup/teardown that starts one server container for the whole run (`testcontainers`, random mapped ports, wait for the "Done" log line) and tears it down after; server and bot logs are attached to failures.
- `test/e2e/support/`: `E2EWorld` helper over RCON (`fill`, `setblock`, `give`, `clear`, `summon`, `kill`, `tp`, `time set`, `gamerule`, block/entity/inventory assertions), a helper that creates the real app via `createApp()` pointed at the container, and an MCP test client to call tools like the agent would.
- Per-test isolation: each test uses its own coordinates, resets the area, inventory, and mobs through RCON before running, and cleans up after.
- E2E tests are grouped by feature in `test/e2e/<feature>/` (for example `movement-perception/`, `survival-reflexes/`), never named with phase numbers. Scripts: `test:e2e -- <feature-dir>` runs only that feature's tests, and `test:e2e:all` runs the complete suite. Neither is part of `npm test`; there is no coverage gate; a clear failure message when Docker is unavailable.
- **Tests (the first e2e scenarios, covering Phases 2 and 3):**
  - the bot connects to the real server, appears in the player list, `say` shows up in the server log, and a chat message sent through RCON `tellraw`/a second bot reaches `wait_for_chat`
  - `goto` to coordinates and `follow_player` (player simulated by a second Mineflayer bot or RCON `tp`), and `stop` interrupts a running move
- **Exit criteria:** running only `test/e2e/movement-perception` starts the server, passes the smoke scenarios, and cleans up the container; the phase's tests are reliable across 5 consecutive runs.

### Phase 5: Persistent state (1.5 sessions)

- Branch: `feature/persistent-state`.
- Ports: `StateStore` (load/save versioned JSON documents by key), `WorldIdentifier` (produces a world fingerprint from the connection). Implementation: `FileStateStore` with atomic write (temp file + rename), a backup copy, schema versions with migrations, debounced writes, flush on shutdown, and a fallback to empty state with a warning when a file is corrupt.
- **World profiles.** Data lives under `DATA_DIR/<profile>/`. On connect, `WorldIdentifier` builds a fingerprint from whatever signals the spike showed to be stable (candidates: hashed seed, world name from the MOTD, world spawn point, dimension). Resolution order:
  1. fingerprint matches a stored profile → use it automatically
  2. no match and no stored profiles → create a profile named after the detected world name (or a generated one) and store the fingerprint
  3. ambiguous or no usable signals → fall back to the name given by the user (`WORLD_PROFILE` or `connect(profile)`); if none was given, the session briefing asks the agent to ask you
  Tools: `list_worlds`, `set_world_profile`.
- **Task journal** (`TaskJournal`, built on `TaskManager` events): records each task's tool, parameters, status, and progress checkpoints. After a relaunch, unfinished tasks appear as `interrupted` with their progress. Tool `resume_interrupted_task` (and `discard_interrupted_task`); nothing resumes automatically because the world may have changed.
- **Standing instructions:** policies and settings set through tools (threat overrides, storage policy later) are stored and restored per profile.
- **Instruction and event log:** append-only JSON lines of your chat instructions, tool calls with results, and reflex events; bounded and rotated. Tool: `get_recent_history`.
- **Agent notes:** `remember`, `recall`, `forget`: free-text notes with optional tags (for example "house plan", "player prefers oak", "base is at ..."), independent of the Claude session.
- **Session briefing:** `connect` (and `get_session_briefing`) returns the resolved world profile, time since the last session, interrupted tasks, standing instructions, key landmarks, recent history, and notes. The runtime protocol requires the agent to read it first and tell you in chat what it found.
- Later features (reflexes' overrides, storage, discovery) build on `StateStore`; the `WorldKnowledgeStore` is a thin domain layer over it.
- **Tests:**
  - unit: `FileStateStore` (atomic write, backup recovery, corrupt file, migration, debounce and flush), world profile resolution (match, new world, ambiguous, no signals, name fallback), `TaskJournal` (checkpoints, interrupted detection), history rotation, notes CRUD, briefing composition, all with a fake `Clock` and an in-memory or temp-dir store
  - integration: run a task, "kill" the app, create a new app instance on the same temp directory: the task is listed as `interrupted`, standing instructions and notes are restored, the briefing is correct; two profiles stay isolated; a different fingerprint does not load the old profile
  - e2e: connect to the Docker server, save a landmark and a note, restart the app, reconnect to the same world (fingerprint match, no name given) and get the same briefing; a re-created world with a different seed gets a new profile
- **Exit criteria:** after relaunching the MCP server and reconnecting to the same LAN world, the briefing shows the previous session; an unfinished task is offered for resume, and a different world does not see the old world's data.

### Phase 6: Survival reflexes (1 session)

- Reflex engine: priority arbitration, preemption/resume of the current task, event log.
- Reflexes: `AutoEat`, `ThreatResponse`, `AvoidLava`, `Drowning` (surface for air). `FallDamageGuard` and `NightShelter` are deferred: the pathfinder's default maximum drop already avoids large falls, and both need placing blocks or buckets, which fits better after the building work.
- Port: `Combatant` (attack an entity respecting the 1.21 attack cooldown, equip best weapon and armor, retreat). `ThreatResponse` and, later, hunting both use it.
- `ThreatResponse` follows the threat policy table in AGENTS.md: flee from skeletons and creepers, flee whenever health is at or below a threshold (default 8 of 20, env-configurable), fight every other hostile mob (equip best weapon and armor first), ignore endermen (never attack them). Fleeing means sprinting away until the threat is out of range and out of sight, preferring the direction of the owner or a known landmark.
- Event log integrated into `wait_for_chat` output.
- Branch: `feature/survival-reflexes`.
- **Tests:**
  - unit: each reflex against fake `VitalsReader`, `EntityScanner`, `Navigator`; `ThreatResponse` policy table exhaustively (skeleton/creeper flee, low health flee overrides fight, zombie/spider fight, enderman ignored, boss flee, threshold boundary); reflex engine arbitration by priority
  - integration: reflex preempts a running task and resumes it; events end up in the next `wait_for_chat`; reflexes work with no MCP client attached
  - e2e: zombie summoned nearby is fought and killed; creeper and skeleton summoned nearby are fled from; hunger set via RCON triggers eating; enderman is not attacked; low health triggers fleeing
- **Exit criteria:** with no MCP client attached, the bot eats when hungry, avoids lava, and reacts to a zombie; events appear in the next `wait_for_chat`.

### Phase 7: Gathering, crafting, smelting (1.5 sessions)

- Ports: `Digger`, `InventoryReader/Writer`, `Crafter`.
- Skills: `CollectBlocks` (find, path, dig, pick up drops, tool selection; own implementation, cancellable via `AbortSignal`, honors protected areas, returns typed failure reasons), `PickupItems`, `CraftItem` (recipe resolution with automatic sub-crafts, crafting table placement when needed), `SmeltItems` (furnace placement, fuel handling).
- Tools: `collect_block`, `pickup_items`, `craft`, `smelt`, `list_recipes`.
- Safety: refuse to dig protected areas; avoid digging straight down; when the inventory is full, stop with a typed, resumable `inventory_full` state (remembering where to continue); the policy for what to do next (ask, or offload and return) is implemented in the storage phase.
- Branch: `feature/gather-craft-smelt`.
- **As built:** also `ProtectedAreas` (boxes saved per world; tools `protect_area`, `unprotect_area`, `list_protected_areas`) as the `AreaGuard` behind "honors protected areas"; `WindowCrafter`, because Mineflayer's own `bot.craft` failed half way on a real 1.21.1 server (the e2e tests found it); block group names (`logs`, `ores`, `leaves`); `DroppedItemScanner` and `Placer` ports. There is no `InventoryWriter` yet: nothing in this phase needed it (the handover phase adds it). The failure result carries a machine-readable `detail` (mined, remaining) for the storage phase to resume from.
- **Tests:**
  - unit: `CollectBlocks` against fake `BlockScanner`/`Navigator`/`Digger` (found, none nearby, unreachable, no suitable tool, inventory full, protected area, abort mid-way, partial result), recipe resolution and sub-craft planning against fixed recipe data, smelting fuel logic
  - integration: `collect_block` → `craft` chain through the MCP tool layer with a stateful fake world (inventory changes), including cancellation
  - e2e: collect N logs from a prepared tree, craft planks/table/pickaxe, mine ore with the right tool and smelt it; cancellation mid-collect
- **Exit criteria:** from chat, "get 20 logs", "make a wooden pickaxe", "get 10 iron ore and smelt it" complete end to end.

### Phase 8: Hunting and food (1 session)

The tools before this phase cannot hunt: perception can list entities and the reflexes only fight hostile mobs on their own, so there is no way to attack a specific passive animal, chase it, and collect the drops. This phase adds that flow.

- Branch: `feature/hunting`.
- **As built:** as planned, plus `AnimalScanner` (a new port over entity metadata) and `AnimalKiller` shared by `hunt_animals` and `attack_entity`. The goal is `item` + `count` or `species` + `count`. Not built: leash detection (Mineflayer does not expose the lead) and the "pause and wait for `resume_task`" flavor of the low-food decision: the `ask` policy emits a `needs_decision` event and the agent asks the player, and `set_food_policy` makes the decision standing. Cooked food is not deposited in chests yet (the storage feature comes later).
- Reuses: `Combatant` (survival reflexes phase), `Navigator` and `EntityScanner` (movement phase), `PickupItems` and `SmeltItems` (gathering phase).
- `AnimalCatalog` (data table): species → drops and behavior notes (cow: beef and leather, pig: porkchop, sheep: mutton and wool, chicken: chicken and feathers, rabbit: rabbit meat, rabbit hide, and others), plus protection rules that exclude:
  - tamed animals (owner set), animals with a custom name, leashed animals, saddled or ridden animals
  - villagers, iron golems, bees, and other neutral or non-livestock mobs
  - animals inside pens or fences (heuristic: enclosed area near player-built blocks) unless the user says so
  - the last breeding pair per species within the search area (`keep_breeders`, on by default); baby animals are skipped by default
- `HuntAnimals` skill: input is a species list or a target item and quantity (for example 20 raw beef or 10 leather), search radius, time limit, `keep_breeders`, and `cook`. Loop: find candidates → pick the nearest reachable one → approach (animals wander and flee, so re-path with a chase limit and give up on unreachable targets across water or cliffs) → equip the best weapon (sword, then axe, then bare hands) → attack in time with the 1.21 attack cooldown → pick up drops → repeat until the goal is met, no candidates are left, or the time limit is reached. Hostile mobs and low health are handled by the reflexes, which preempt and then resume the hunt.
- `cook: true`: after hunting, run the existing smelting skill on raw meat (furnace, smoker, or campfire when available; fuel handling included); with the storage feature present, cooked food can be deposited according to the storage rules (food category).
- **Low-food policy** (`LowFoodPolicy`, same pattern as the inventory-full policy): when food runs low and the inventory has nothing edible, the bot pauses or emits a `needs_decision` event; options are `ask` (default), `hunt_and_cook` (allowed by the user's instruction on the call or as a standing instruction), and `stop`. Works together with the `AutoEat` reflex, which keeps eating whatever food exists.
- Tools: `hunt_animals`, `list_huntable_animals` (what is around and what is protected), `attack_entity` (explicit single target, for requests like "kill that cow"; refuses protected animals unless overridden), `set_food_policy`.
- Safety: never harm pets or named animals; report species counts before and after; stop when the breeding-pair floor is reached and tell the user.
- **Tests:**
  - unit: `AnimalCatalog` (each protection rule, baby animals, breeding-pair floor), `HuntAnimals` against fake `EntityScanner`/`Navigator`/`Combatant` (nearest-first selection, chase give-up, attack cooldown timing with a fake clock, drop pickup, goal reached by item counts, no candidates, time limit, abort, hostile interruption), `LowFoodPolicy` (ask, hunt_and_cook, stop)
  - integration: hunt → smelt → (deposit) chain through the tool layer on a stateful fake world; a hostile appears mid-hunt, the reflex preempts, the hunt resumes; a low-food task pauses with `needs_decision` and continues after `resume_task`
  - e2e: cows, pigs, sheep and chickens summoned in an area via RCON, `hunt_animals` for N raw beef ends with the items in the inventory; a named cow and a tamed wolf are never attacked; the last breeding pair is preserved; `cook: true` yields cooked meat; with no food and no instruction the bot asks
- **Exit criteria:** "get me 10 steaks" from chat runs the full flow (hunt, drops, cook); protected animals stay unharmed; "if you run out of food, hunt" is remembered as a standing instruction and works.

### Phase 9: Storage and containers (1.5 sessions)

- Branch: `feature/storage-containers`.
- **As built:** everything in this phase except `OrganizeStorage` and "craft and place a new chest" (both in `BACKLOG.md`), plus `remove_container`, `ItemFacts` and `LookTarget` ports, and `WindowTransfer` (moving items by clicking, because Mineflayer's `deposit`/`withdraw` are unreliable on 1.21, like `bot.craft`). Container memory is `ContainerIndex` (persisted through `StateStore`); there is no separate `WorldKnowledgeStore` yet, which the discovery feature can introduce. `waiting_for_input` is a `TaskManager` status with `context.ask` and `TaskManager.answer`. Building integration comes with the building phase.
- Ports: `ContainerAccess` (open chest/barrel/double chest/shulker box, read contents, move items in and out). Mineflayer adapter behind it.
- Container memory in `WorldKnowledgeStore` (persisted per world profile through `StateStore`): position, optional label (`home`, `wood`, `tools`, ...), last-seen contents, last-opened time, optional `protected` flag.
- **Pointing at chests.** A container is registered by any of: explicit coordinates, "the chest I am looking at" (the bot reads the owner's look direction and finds the targeted block), or "the nearest chest to me". Tool: `register_container` (with optional label).
- **Storage rules** (`StorageRule`): "these kinds of items go into that chest". An `ItemMatcher` supports exact item names, item tags/groups (for example all logs, all ores, all food), and categories (tools, food, blocks); rules have priorities, and a catch-all rule is allowed. Example: stone and cobblestone → chest A, ores and ingots → chest B, everything else → chest C. Tools: `set_storage_rule`, `list_storage_rules`, `remove_storage_rule`.
- **Target selection** (`ContainerSelector`, swappable strategy): first matching rule wins; if no rule matches, use any known chest with free space (nearest first), then any unknown nearby chest; if none has room, report `no_storage_space` (optionally craft and place a new chest when allowed by the instruction).
- **Skills:** `DepositItems`, `WithdrawItems`, `FindItems` (search the remembered index first, then open nearby chests to refresh it, and report where an item is), `ScanContainers` (refresh the index), optional `OrganizeStorage` (sort everything according to the rules). Reserve list: tools, weapons, armor, food, and torches are never deposited unless asked.
- **Inventory-full policy** (`InventoryFullPolicy`), used by gathering and any other inventory-filling task:
  - `ask` (default when the user gave no instruction): the task **pauses** in a `waiting_for_input` state (not failed), emits a `needs_decision` event (delivered through `wait_for_chat`), and I ask you in chat; the answer goes back via `resume_task`.
  - `offload_and_return`: allowed by your instruction, either on the call (`on_inventory_full`) or as a standing instruction for the session (`set_storage_policy`, for example "feel free to bring resources to the home chest iteratively when there is no space left"). The task remembers its position, walks to the target container chosen by the rules, deposits, walks back, and continues. Limits: max trips, max distance, stop conditions (`no_storage_space` → falls back to `ask`).
  - `stop`: end the task with the partial result.
  - Long-task flows such as "gather 100 stacks of stone and build a house from it, bring resources to the home chest whenever there is no space" are composed by the agent from these primitives: `collect_block` with the offload policy, then `build`, with a standing policy carried across the steps.
- `TaskManager` gains the `waiting_for_input` state and pause/resume; tools `resume_task` and `set_storage_policy`, plus the container tools: `deposit_items`, `withdraw_items`, `find_items`, `list_containers`, `label_container`, `register_container`, `scan_containers`.
- Hunting integration: `hunt_animals` with `cook: true` can deposit the cooked food into the chest designated by the food rule, and the inventory-full policy applies to hunts as well.
- Building integration (in the building phase): `build` reports missing materials and can fetch them from the container index when the policy allows.
- Safety: never take from or empty containers marked `protected`; report what was moved; handle full, missing, and destroyed containers gracefully (the index is refreshed on mismatch).
- **Tests:**
  - unit: `ItemMatcher` (names, tags, categories, precedence), `ContainerSelector` (rules, fallback to any chest, no space), deposit/withdraw against a fake `ContainerAccess` (partial fits, full chest, double chest, missing item), `InventoryFullPolicy` (ask vs offload vs stop, trip limit, fallback), `TaskManager` pause/resume, container index persistence
  - integration: gather task hits inventory-full → pauses and emits `needs_decision` → `resume_task` continues; with `offload_and_return` it makes several deposit trips without asking and finishes the whole quantity; rules route different item kinds to different chests; `WorldKnowledgeStore` on a temp directory keeps containers and rules across app restarts
  - e2e: fill chests via RCON and `find_items` locates the item across several chests; deposit routes stone, ores, and misc to three different chests by rule; a gather task with a small inventory (filled via RCON) completes through repeated offload trips; without instruction the task pauses and asks
- **Exit criteria:** "these chests hold those items" rules are remembered across restarts; "get all my iron from the chests" finds it; the flow "gather N stacks of stone, offload to the home chest when full, then continue" runs end to end, and the same flow without instruction asks first.

### Phase 10: Item handover (½ session)

Today there is no way to hand items over: the inventory port can drop items, but no tool exposes it, and nothing walks to a player, chooses what to give, or fetches it from storage. This phase adds that flow.

- Branch: `feature/item-handover`.
- **As built:** as planned. The request words are resolved by the server (`ItemResolver`), and the agent passes them as the player said them; `InventoryWriter` and `Gaze` are new ports. Not built: a retry that collects the items again when nobody picked them up (the result reports `unclaimed`; the drop-recovery feature takes them back), and telling the dimension of an unseen player apart from a far-away one.
- Reuses: `Navigator` (go to the player), `InventoryReader/Writer` (toss), and the storage feature (`FindItems`, `WithdrawItems`) as the source of items.
- `ItemResolver`: turns what you say ("iron", "some wood", "a stack of cobble", "food") into concrete item ids and counts, using minecraft-data names, plurals, and item groups. When the request is ambiguous ("wood" could be logs or planks) it returns candidates so that I ask you in chat. Counts like "a stack" or "all" are supported.
- `GiveItems` skill: input is the player (defaults to the owner), the items, and options (`fetch_from_storage`, default on; `keep_reserve`, default on; `mode`).
  1. Source: take from the inventory first, then from remembered chests (walks there, withdraws, returns), then report a typed `shortfall` with exactly what is missing so that the agent can offer to gather, craft, or hunt.
  2. Reserve: tools in use, armor, weapons, and food are not given unless named explicitly.
  3. Delivery: find the player (they may be far away; go to them, and report if they are in another dimension or unloaded), approach to about 2 to 3 blocks, face the player, and toss the items so they land at the player's feet, splitting into stacks with a short delay. Check that the drop spot is safe (not lava, water, or a ledge).
  4. Aftercare: step back so the bot does not re-collect its own drop right away, and verify the dropped item entities disappear (were picked up). What happens to items nobody picks up is decided by the drop-recovery feature (next phase): by default the bot collects them back after a timeout, unless the user said to leave them.
  5. `mode: chest`: for large amounts (many stacks), put the items in a chosen or nearby chest instead, and tell the player which one.
- Tools: `give_items`, `drop_items` (drop at the bot's own position, for example to get rid of junk; respects the reserve), and `resolve_item` (shows what a phrase maps to). The reverse direction, you giving items to the bot, needs no new tool: you drop them near it and `pickup_items` collects them.
- Safety: only the configured owner's requests count as instructions (`MC_OWNER`); never give items that are marked reserved or come from `protected` containers without confirmation; report exactly what was given.
- **Tests:**
  - unit: `ItemResolver` (names, plurals, groups, "a stack", "all", ambiguity candidates), `GiveItems` against fake `Navigator`/`InventoryWriter`/storage ports (source order inventory then chests, shortfall report, reserve rules, stack splitting, approach distance, unsafe drop spot, pickup verification and retry, player gone or in another dimension, abort)
  - integration: "give me 3 stacks of cobblestone" through the tool layer on a stateful fake world with items split between inventory and a chest; shortfall returns the missing counts; chest mode
  - e2e: a second Mineflayer bot acts as the player (its inventory is inspectable): `give_items` delivers the requested items; items fetched from a chest filled via RCON; shortfall case; reserved tools are not given; chest mode with many stacks
- **Exit criteria:** "give me 20 iron ingots" from chat makes the bot fetch them from the inventory or chests, walk to you, and drop them at your feet; you receive them, and if they are not enough the bot tells you exactly what is missing.

### Phase 11: Drop recovery (1 session)

The plan had no death handling at all, and nothing about items the bot has dropped that end up lying around. This phase makes recovering the bot's own drops automatic by default, and skippable whenever you ask.

- Branch: `feature/drop-recovery`.
- **As built:** as planned, with these differences. (1) There is no `DeathReflex` in the reflex engine: the engine polls every 250 ms and Mineflayer respawns the bot at once, so a death could fall between two ticks. Instead a `DeathWatcher` port reports the death from the bot's own events, and `DeathResponder` (plain code, like `LowFoodResponder`) reacts. The death is reported at the respawn: the server's death message has arrived by then, and the inventory before the death is taken from the last look before the fatal hit if the server had already emptied it. (2) keepInventory is not read from a game rule (the bot cannot): the inventory before the death is compared with the one two seconds after the respawn, and nothing lost means nothing to recover. (3) `AutoRecovery` starts the recovery task by itself (waiting for a running task or an acting reflex, for about three minutes) and tells the agent and the game chat how it went; `UnclaimedDropHandler` does the same for handover leftovers. (4) The unclaimed wait is the setting `UNCLAIMED_DROP_WAIT_SECONDS` (default 60), counted from the throw. (5) `list_death_records` lists both kinds of records. (6) After a restart nothing is recovered on its own: the session briefing lists the drops that can still be fetched (`pendingDrops`), and the agent asks the player. (7) A shield is put in the off hand together with armor and weapon (`equipBestGear`). (8) A bot that died while it was recovering does not go back on its own; it tells the agent instead.
- Two situations covered:
  1. **Death drop:** the bot died and its inventory lies at the death spot (items despawn after 5 minutes).
  2. **Unclaimed handover drop:** items dropped for a player that nobody picked up.
- `DropRecoveryPolicy`: `auto` (default) or `skip`. Set as a standing instruction (`set_drop_recovery_policy`, optionally per situation), or per call (`give_items(recollect_unclaimed: false)`), or told in chat at any moment ("forget it, do not go for it"), which calls `skip_drop_recovery`: any running recovery is cancelled, and the record is kept as `abandoned` with coordinates so you can fetch it yourself. Skipped or abandoned drops can be recovered later on request (`recover_drops`).
- Even in `auto`, the bot never wades into lava, void, or other hazards: when the spot looks unsafe it pauses in `waiting_for_input` with a `needs_decision` event and reasons, and I ask you.
- `DeathReflex` (a reflex in the existing reflex engine): detects death, respawns, and records a `DeathRecord` (position, dimension, time, cause, snapshot of the inventory before death, so it knows what was lost), saved through `StateStore` so it survives a relaunch. Emits a `bot_died` event and a chat message with the coordinates. If keepInventory is on, no recovery is needed and it is skipped.
- `RecoverDrops` skill:
  - hazard assessment of the death spot from a safe staging point (lava, void, deep water, fire, cacti, hostile mobs, wrong dimension), then approach with the safe movement profile
  - deadline: death time + 5 minutes minus a safety margin; if the ETA exceeds it, say so instead of trying
  - pick up all item entities around the spot (drops scatter), then re-equip armor, weapon, tools, and shield
  - report recovered versus lost items (from the pre-death snapshot)
  - max attempts (default 2) so it cannot loop into repeated deaths
- Unclaimed handover drops: after the pickup-verification timeout (default 60 s), with `auto` the bot collects the leftover items and tells the player; with `skip` (or `recollect_unclaimed: false`) it leaves them.
- `DropIgnoreList`: items the bot deliberately dropped (for example junk via `drop_items`) are never auto-recollected.
- Tools: `set_drop_recovery_policy`, `skip_drop_recovery`, `recover_drops`, `list_death_records`.
- **Tests:**
  - unit: `DeathReflex` (record contents, keepInventory case, persistence), `RecoverDrops` against fake scanners and navigator (hazard detected → asks, deadline math with a fake clock, max attempts, partial recovery report, re-equip), policy handling (auto, skip, cancel a running recovery, recover later), ignore list, unclaimed-drop logic
  - integration: bot dies → record persisted → app restarted → record still there and recovery proceeds or is offered; skipping mid-recovery cancels it and reports the coordinates; unclaimed handover drop is recollected in `auto` and left in `skip`
  - e2e: the bot holding items is killed through RCON, respawns, and recovers its items automatically; "skip" leaves them and reports the coordinates; a death spot surrounded by lava (built via RCON) leads to asking and not to a second death; an unclaimed handover drop is collected back after the timeout, and left when `recollect_unclaimed` is false
- **Exit criteria:** after the bot dies, it tells you where and recovers its stuff by itself; telling it to skip stops the attempt and gives you the coordinates; a dangerous spot is never entered without asking you.

### Phase 12: Server commands and teleport (½ session)

The bot can walk to you, but sometimes you want it next to you at once (it is far away, in a cave, or across water). When the server allows commands, it can teleport to you.

- Branch: `feature/server-commands`.
- **As built:** as planned, with these details. Availability comes from the `declare_commands` packet (the server sends the commands this player may use, and sends the list again when operator rights change), read by `commandNamesFrom` and kept on the bot by the factory; there is no probe command, because a command that is not on the list is exactly one the bot may not run. Replies are told apart by wording (`classifyReply`, pure): vanilla shows "Unknown or incomplete command" for a command the player may not use, so the list decides between `no_permission` and `unknown_command`. A server with command feedback off gives no reply (`sent`), and the skill then checks that the bot really moved. `TeleportSkill` uses `/tp @s <player>` or `/tp @s x y z`, and for a player target steps to a safe spot next to them (`SafeSpotFinder`, waiting for the chunks to arrive). There is no generic "run any command" tool, on purpose: every command that gets a tool decides for itself when it may be used.
- **What the server must allow:** on a LAN world "Allow cheats" must be on, **and the bot must be an operator** (`/op ClaudeBot`, typed by you as the host; cheats alone only make the host an operator). The bot cannot grant this to itself. Without it the tool answers `no_permission` with these instructions, and the agent offers walking (`goto`) instead.
- Port `ServerCommands`: `available(command)` (from the command tree the server sends at login, with a harmless probe as fallback) and `run(command)`, which sends the command, waits (bounded) for the server's reply in chat, and classifies it: `ok`, `no_permission`, `unknown_command`, `error` (with the server's text). Reusable later for the optional `/locate` accelerator in world discovery.
- Tools: `teleport_to_player` (player defaults to the owner) and `teleport_to_position`. **Only on your request**: the description tells the agent so, and no reflex or task ever teleports on its own. `get_status` reports whether commands and teleporting are available.
- Arrival: `/tp` puts the bot at the player's exact position, so it steps aside to a safe standing spot next to them (not in a wall, over lava, or in the air), and reports where it stands.
- **Tests:** unit: reply classification (success, no permission, unknown command, other errors, timeout), availability from a command tree, `TeleportSkill` (safe spot search, denied, timeout, aborted); integration: the tool through the MCP layer with a fake connection; e2e: the bot is opped through RCON and teleports to a player standing far away (arrives within 3 blocks, on solid ground); without op the answer is `no_permission` with the explanation.
- **Exit criteria:** "teleport to me" puts the bot next to you when commands are enabled, and explains exactly what to enable when they are not.

### Phase 13: Construction engine and building (2 sessions)

**Design decision: one shared engine, not one big feature.** Building, excavation, and railways all do the same thing: turn a shape into an ordered list of block operations (break here, place there, light there), then carry it out safely, resumably, and within the bot's means (tools, materials, light, hazards). Their differences (what shape, what stops it) are small. Merging them into one feature would make one huge, untestable branch; keeping them apart would build the same executor three times. So this phase builds the engine and delivers **building** as its first client, and the excavation and railway phases are further clients that add only their shape generators and rules.

- **`WorkPlan`**: an ordered list of `WorkStep`s (`break` a cell, `place` a block at a cell against a support face, `light` a spot, `check` something), plus where the bot should stand for each. Shape generators implement `PlanProvider` (Open/Closed: a new shape is a new class): blueprints for building here, `ExcavationProvider`s in the excavation phase, a rail route provider in the railway phase.
- **`PlanExecutor`**: runs a plan step by step with walking between standing spots, tool choice and durability (swap to a fresh tool, craft one, or stop `no_tools`), material accounting (a **preview** reports what is missing before anything is done, so the agent can gather first), the inventory-full policy from the storage phase, protected areas, a persisted cursor so an interrupted plan resumes where it stopped, a verification pass, and retries of failed steps. Reflexes pause and resume it like any task.
- **`SiteSafety`** (shared by every client): the *hazard envelope* check (fluids, falling blocks, cave breakthroughs, drops: see the excavation phase) and the `LightManager` (reads the light level of the spot, places a torch when it is below `min_light` and no torch is closer than the spacing; crafts or fetches torches).
- `Placer` grows `placeAgainst(reference, face)`, so torches go on walls, stairs and rails face the right way, and blocks can be placed from the side or from below.
- **Building on top of it** (original scope of this phase): domain `Blueprint` (relative block placements) and the `BlueprintProvider` registry. Providers: `Box`/`Walls`/`Floor`, `Shelter` (1×2 emergency), `SmallHouse`, plus a JSON blueprint loader for custom builds. `BuildSkill` = `PlanExecutor` over a blueprint plan. Tools: `build`, `list_blueprints`, `place_block`, `preview_build`. Missing materials can be fetched from the container index (the storage phase's `FindItems` and `WithdrawItems`).

- Branches: `feature/construction-engine` (the engine, with a first building client) and `feature/building` (the blueprint library, the house, and pillaring up).
- **As built in `feature/building`:** the providers `house` (floor, walls, flat roof, a doorway with a real door, optional windows, torches), `shelter` (a sealed 1×2 room built around the bot from the inside; no origin needed) and `custom` (any shape the agent writes out as layers of characters plus a legend, in the tool call itself, so there is no file format to maintain), and pillaring up (`Scaffolder`). Differences from the plan text: (1) doors are placed with the bot standing in line with the doorway (`alignAxis` on a place step, honoured by `StandingSpotChooser`), because a door's orientation follows where the bot looks; (2) the default scaffold block is **dirt**, not cobblestone: cobblestone dropped by hand gives nothing, so the tower blocks would be lost (the tool description says so); (3) a tower left standing after a crash or a disconnect is **not** removed automatically (cancellation and failures always descend first); the executor does not persist tower records; (4) stairs, pitched roofs, and beds inside houses are left out: they need block facing beyond doors (stairs and roofs are in the backlog; beds come with the sleeping feature).
- **Pillaring up (scaffolding), in `feature/building`.** Reach is about 4 blocks, so a wall taller than that, a second floor, a roof of a tall house, or a tower cannot be built from the ground. When the `StandingSpotChooser` finds no spot within reach of a step, the executor asks a `Scaffolder` to raise the bot:
  - It jumps and places a cheap block under its own feet (dirt or cobblestone from the inventory, chosen by a `scaffold_block` parameter with a default), one block at a time, until the step is in reach; it does the reachable steps from up there, and when it is done, **takes the tower down again from the top** (breaking the block underfoot, one drop at a time) and picks the blocks back up, so no scaffold is left and the blocks are reused. The tower stands outside the volume being built when possible, or on a spot that a later step will fill anyway.
  - `preview_build` counts the scaffold blocks as extra materials (reusable, so it counts the tower height, not every step), and reports the maximum height it will climb (default 12, a parameter).
  - Safety rules: never pillar in or next to a protected area, under a ceiling with less than two blocks of room, over or next to lava or water, or beyond the height limit; if the bot is cancelled or the plan fails while it is up, it comes down first (the drop is never more than one block at a time). No fall-damage risk by design: the descent is by breaking the block underfoot, not by jumping off.
  - New pieces: a `Scaffolder` in the construction folder (uses `Locomotion` for the jump and `Placer.placeAgainst` for the block under the feet), a `raise`/`lower` step kind inside the executor, and tower bookkeeping so an interrupted build can remove a tower it left (the executor looks for its scaffold blocks when it resumes). Excavation (shafts, climbing out of pits) and cave exploration can reuse it later.
- **As built in `feature/construction-engine`:** `WorkPlan` (steps `place`, `break`, `light`), `PlanExecutor`, `StandingSpotChooser`, `SiteSafety` (lava in or beside the site; torch spacing), `Placer.placeAgainst`, the `LightReader` port, `BlueprintProvider` with `BlueprintRegistry`, the providers `floor`, `walls`, `box` (floor, walls, roof, a 1×2 doorway by default, optional torches), `solid` and `block`, `BuildSkill` (with `StorageMaterialFetcher`), and the tools `build`, `preview_build`, `list_blueprints`, `place_block`. Differences from the plan text: (1) there is **no persisted cursor**: the world itself is the cursor. Every step whose result is already in the world is skipped and a second look at the end verifies the result, so an interrupted build simply continues when it is run again (the task's resume descriptor holds the same arguments). (2) The order is **support-first**: the executor takes the first step that has something to be placed against, so walls grow from the ground up whatever order a provider lists them in. (3) The bot avoids standing inside the volume it is building when it has a choice, so the last blocks do not seal it in; the `box` doorway is the other half of that. (4) Tool durability swapping and crafting a replacement tool are **not built yet** (a block that needs a tool the bot lacks stops the plan with `no_suitable_tool`); they arrive with excavation, where tools wear out. (5) Pillaring up is **not built in this branch** but is a firm part of `feature/building` (below): a small building is reached from the ground and from the inside, and taller ones need the scaffold. (6) Missing materials are fetched from containers with the storage feature's withdraw skill, then whatever is still missing is reported.
- **Tests:**
  - unit: `PlanExecutor` against a grid-based fake world (ordering, standing spots, tool swap, material preview, resume from the cursor, verification, retries), `SiteSafety`, blueprint providers (deterministic output, dimensions, door position, material counts), `BuildSkill` (missing materials, scaffold counts in the preview), `Scaffolder` (climbing to the needed height, tower removal from the top, a ceiling or lava or protected area or the height limit stopping it, cancellation while up comes down first, resuming removes a leftover tower)
  - integration: `build` through the tool layer on a stateful fake world produces the expected block grid
  - e2e: build a small house on flat ground from supplied materials, then verify the block layout in the world through RCON; missing-materials report when the inventory is empty; a wall or roof higher than the reach is built by pillaring up, the tower is gone afterwards and its blocks are back in the inventory, and the bot stands on the ground
- **Exit criteria:** "build a small house here" gathers or reports missing materials, then produces a complete, enterable house with a door; a building taller than the bot can reach (for example walls 7 blocks high or a second floor) is finished by pillaring up, leaving no scaffold behind and the bot standing on the ground.

### Phase 14: Excavation and mining (3.25 sessions)

`collect_block` is deliberately conservative: it only digs blocks that touch open air, never tunnels, and never digs straight down (that is why "dig a 3×3×2 pit" is refused). Digging pits, quarries, tunnels, and mines needs its own tool, with its own rules and a plan you can preview.

- Branches: `feature/excavation` (the shapes, the hazard rule, light, ore veins, ladders), `feature/excavation-extras` (the rest of this list, marked *later* below), `feature/excavation-cave-sealing`, `feature/excavation-stair-sizing`, and `feature/excavation-staircase-target` (the last three found live, below). Built on the construction engine (`WorkPlan`, `PlanExecutor`, `SiteSafety`).
- **As built in `feature/excavation`:** shapes `pit`, `shaft`, `quarry` (default target 9 above the bedrock), `tunnel`, `branch_mine`, `staircase_down`, each a provider that validates its own numbers and echoes them in `preview_excavation`; `HazardRule` (lava or water in the block or any of the six that touch it ends that chain one block short; also an open cavity ahead (`cave_breakthrough`), sand or gravel overhead, spawners, chests, rails and furnaces, and unloaded blocks; results list every ended chain with the reason and the place); chains and dependencies (`branch`, `needs`: a cell is only dug when the one before it is open, so a branch never digs through rock on its own, and branches beyond a short main tunnel are reported `blocked_by_earlier`); torches by spacing with `no_torches` when they run out; ore veins mined by flood fill (up to 64 blocks, never into protected areas or next to fluids); **ladders** up the west wall of pits, shafts and quarries, placed layer by layer, so the bot climbs out by itself (the pathfinder climbs ladders; the e2e test walks out of a pit). Tools `excavate`, `preview_excavation`, `list_excavations`.
- **As built in `feature/excavation-extras`:** `exit: stairs` (a helical staircase around the footprint, walkable out of the pit; the water landing needs no wall stairs because the bot can also use them), `water_landing` for quarries (2×2×2 pond in the far corner, two bucket placements), `spoil_policy: discard_junk`, torch crafting on `no_torches`, and a spare pickaxe crafted when the needed tool is missing (durability awareness is this: no separate wear tracking). `seal_hazards` was dropped: the hazard rule never opens a face to fluid, so nothing needs sealing.
- **Known open item:** the stairs e2e (`test/e2e/excavation/extras`) failed intermittently on one side assertion (the block under stair step 1 being dirt), then passed 9 runs in a row; the cause is not found (see AGENTS.md, e2e gotchas). Revisit it at the final hardening gate with a repeated run of that file.
- **Cave sealing** (done, `feature/excavation-cave-sealing`, about 0.75 session). **Found live:** digging a quarry with `exit: stairs`, a cave that touched or crossed the footprint left unintended openings in the quarry's own walls and floor ("air walls" where solid rock should have stayed), and could leave a stair step with nothing solid to stand on; this affected the dug result and could stop the walk-out. Two related gaps, both fixed here:
  1. `pit` and `quarry` dig with `cavityCheck: false` (unlike `shaft`, which already checks): the reasoning was "open to the sky, no cave to break into," which only covers the open top, not a cave crossing the sides or the floor at depth. Fixed by giving them `cavityCheck: true` too, so every shape stops one cell short of a cave the same way (`cave_breakthrough`), instead of a quarry or pit digging straight through into one unnoticed.
  2. Even where the dig correctly stops short of a cave, nothing repairs a boundary, or a designed stair or ladder step, that a cave has **already** hollowed out before the dig gets there: the existing rule only ever avoids breaking further rock, it never places rock back. A **new seal pass** covers this: wherever a plan needs a cell to stay solid (a wall, floor, or ceiling cell at the boundary of `hazards: 'end_branch'`, and every ring cell of `exit: stairs` or the ladder column of `exit: ladder`) and that cell is already open and not the dig's own (the same `isOurOwn` test the hazard rule already uses, so mined cells and ore veins are never mistaken for a cave), a block is **placed** there (`seal_block`, default `cobblestone`, falling back to `dirt` when none is carried) instead of the opening being left as it is. This is what closes the holes the player found: a quarry wall or floor a cave had already opened, and a stair step with no material underfoot.
  3. **A sealed breach can be worked past, instead of ending the branch for good.** Where a column, tunnel, or branch meets a cave (`cave_breakthrough`), sealing the opening lets it carry on past the cave to its full planned extent (a quarry column still reaches its target depth, with the cave wall closed behind it), rather than stopping there permanently, which is the "affects the result" the player saw (a column or branch left too shallow because a cave happened to cross it).
  - Applies to every shape that excavates, not only quarry: pit, shaft, tunnel, branch_mine, staircase_down, and Phase 16's `room`.
  - Off with `seal_caves: false` (default true) for a player who wants to break into a found cave on purpose and explore it (`explore_caves`, Phase 22, is the tool for that); excavation defaults to closing what it finds, since a dig was not asked to open a cave.
  - The previously dropped `seal_hazards` idea (`feature/excavation-extras`) only ever covered fluids, which never needed it, since the hazard rule already stops one block short of lava and water and no face is ever exposed there; this is the missing dry-cave case, and it is the reason `seal_hazards` is revived here under the clearer name `seal_caves`.
  - **Tests:**

When the phrasing is ambiguous (for example which of three numbers is the height), the agent asks, and `preview_excavation` echoes the interpreted dimensions, so a wrong reading is seen before anything is dug.
- **The hazard rule** (the rule about lava and water, stated precisely). Before the bot breaks any block, it looks at that block and at the six blocks that touch it, and at the cells that will become the wall, floor, and ceiling beside the new opening. **If any of them is lava or water (source or flowing), the block is not broken and that branch ends there**: breaking it would let the fluid flow into the tunnel. With `seal_hazards` the exposed face is plugged with a solid block; either way the result records `hit_lava` or `hit_water` with the position, and the other branches carry on. The same check also ends a branch on: an open cavity or ravine ahead (a *cave breakthrough*, recorded so cave exploration can use it, and lit), a column of sand or gravel directly above the opening (it would fall in: supported with a block, or the branch ends `falling_blocks`), a monster spawner (reported, never broken), unloaded chunks, chests and rails and other player-placed blocks, and protected areas.
- **Safe vertical work:** the bot never digs the cell it stands on unless the plan is a designed stair, it never stands where the cell below is lava, void, or a drop of more than 3, and quarries are dug in layers from a ramp, so there is always a walkable way out.
- **Light** (shared `LightManager`): a torch is placed whenever the light at the bot is below `min_light` (default 7; monsters spawn only at light level 0 in 1.21, so anything above 0 stops spawning and 7 also keeps it visible), and at least every `torch_spacing` blocks in tunnels (default 6), on alternating sides of quarry stairs, and at every branch junction. Torches are crafted (coal or charcoal + sticks) or fetched; with none left the work stops with `no_torches`, and the agent asks.
- **Ores:** any ore that touches the dug space is mined, vein by vein (a flood fill with a size limit, under the same hazard rule). The bot does not use its knowledge of buried blocks to steer towards ores: it digs the pattern, as a player would.
- **Spoil:** a big quarry moves thousands of blocks. **By default it follows the standing storage policy** (`set_storage_policy`: ask, offload and return, or stop), like every other task; nothing new is decided silently. A request can say otherwise, per call or as a standing instruction: `spoil_policy: discard_junk` (drop cobblestone, dirt, gravel, deepslate, and the like beyond a small stock, away from the work) or `offload` (chests by the storage rules).
- **Tools:** the best pickaxe (and shovel for soft blocks); when durability runs low it takes the next one, crafts a spare if the materials are there, and otherwise stops with `no_tools`. Food and threats are handled by the reflexes, which pause and resume the work.
- **Progress and resume:** the plan cursor is saved, so an interrupted dig (a disconnect, a fight, a full inventory) resumes from where it stopped.
- **Tools (MCP):** `excavate` (a `shape` plus its parameters and the options above; sizes as separate numbers), `preview_excavation` (block count, tool wear, torches, buckets, and time estimate, and what is missing), and the results describe every branch that ended early.

### Phase 15: Structured gathering: pits and quarries instead of scattered holes (1 session)

Found live: gathering a bulk terrain block (dirt, stone, cobblestone, sand, gravel, netherrack) through `collect_block` digs the nearest matching block wherever one happens to be, one at a time. For a big request this leaves a scatter of small, uneven single-block holes across the area instead of one clean dig, and looks like vandalism rather than mining. Builds directly on excavation (Phase 14) and needs nothing else, which is why it comes right after it, before site preparation and the rest.

- Branch: `feature/structured-gathering`. A client of the excavation providers and the construction engine; no change to the shapes themselves.
- **What counts as "bulk."** A new small group in `block-aliases.ts` (alongside `logs`, `ores`, `leaves`): `terrain`, the plain, common blocks that come back one-for-one from a single break and need no searching to find, because they are simply the ground: `dirt`, `stone` (which drops `cobblestone`), `cobblestone`, `sand`, `gravel`, `netherrack`. Ore is deliberately excluded: a quarry does not help you "find" ore, since you dig it wherever it happens to be, so ore keeps the scattered nearest-first hunt.
- **When it switches.** `collect_block` gains `layout` (`auto` default, `scattered`, `structured`) and `structured_threshold` (an item count, default 5; also settable as a standing instruction). `auto` uses a structured dig only for a `terrain` block requested at or above the threshold; anything else (ore, wood, a small request) keeps today's scattered behaviour unchanged. The player can force either way regardless of block or count: `layout: structured` for a small, tidy hole on purpose, `layout: scattered` to keep the ground undisturbed for a big one (no new pit wanted right now). A structured dig only ever targets material that is actually at the site (the block requested must be the one right under the dig's own origin); otherwise it is not suitable and falls back to scattered, the same as a protected or unsafe site. A single-layer dig gets no exit built (nothing to climb out of), so a small request near the threshold is not saddled with a full staircase for a shallow scrape.
- **Sizing the dig.** For a one-for-one block, the skill picks a `quarry` footprint and depth whose total cell count is close to the requested count, biased toward a small, roughly square footprint (never wider than about 5 by 5) over a deep, narrow shaft, and capped by the same size limits `excavate` already enforces. A count that does not divide evenly rounds up to a whole layer and reports the surplus, the same way an overshoot is already described in `collect_block`'s result.
- **Where it digs.** Beside the bot, on the flattest, most open ground nearby: the same "is the site safe and clear" check the excavation shapes already do before starting (no lava in or next to it, no obstruction, not a protected area, not inside a player-made structure) decides whether the spot works. When nothing suitable is close by (a cliff edge, water, builds on every side), it falls back to the scattered dig and says why in the result, rather than refusing the request outright.
- **What it reuses, unchanged.** The dig is a real `excavate` quarry under the hood: the hazard rule, cave sealing, an exit ladder by default so neither the bot nor a player who follows gets stuck at the bottom, and the same spoil and inventory-full policies that already apply to every dig.
- **Reporting.** The result names what it did (`layout: structured`, the shape, and its origin) so the player knows where the hole is and can reuse or fill it later, alongside `gained`, exactly as `collect_block` already reports it.
- **Tools:** no new tool; `collect_block` gains `layout` and `structured_threshold`. The excavation preview (`preview_excavation`) already exists for a player who wants to check a shape by hand first.
- **Tests:**
  - unit: the `terrain` group (membership, `stone` mapped to its `cobblestone` drop, ore excluded), the `auto`/`scattered`/`structured` decision at and around the default and a per-call threshold, the sizing function (count to footprint and depth, the square bias, the size cap, the rounded-up overshoot and how it is reported), the site check (a flat, open spot found near the bot; refused near a cliff, water, or a protected area, with the scattered fallback and its reason)
  - integration: `collect_block` with a bulk request over the threshold on a stateful fake world produces a quarry-shaped dig (checked by the shape of the hole, not by scattered positions) and reports `gained`; a small or named-ore request still digs scattered, unchanged; no flat ground nearby falls back to scattered and says why
  - e2e: "get me 40 dirt" on open ground digs one small, contained quarry (checked through RCON: a solid rectangular footprint, not scattered single-block holes) and the inventory gains at least 40 dirt; "get me 3 dirt" still digs a few scattered blocks, unchanged; started at a cliff edge, it falls back to scattered and says why
- **Exit criteria:** "get me 40 dirt" (or cobblestone, sand, gravel, or netherrack) leaves one small, contained pit or quarry near the bot instead of a field of scattered single-block holes, with an exit ladder, and the reply says where it dug; a small or specific request behaves exactly as it does today.

### Phase 16: Site preparation: leveling, dug rooms, and opening doors (2 sessions)

Three features that prepare a place for building or living, each on its own branch: `feature/site-leveling` (about 1 session), `feature/dug-rooms` (about 0.75), and `feature/door-opening` (about 0.25). The first two are clients of the excavation machinery and the construction engine; the third belongs to movement.

#### Site leveling (`feature/site-leveling`, done)

**Built as planned, with a few narrowings, noted here rather than left silent:**
- **Landmark saving (`label`) was not built.** `set_landmark`/`list_landmarks` are Phase 22 (discovery), not built yet, so there is nowhere to save a plot's name and bounds to. The result still reports `bounds` and `level` so the agent can pass them straight to `build`/`build_farm`.

It also has to consider many more than a couple of nearest matches (`count: 400`, found while writing the e2e test): dirt and cobblestone are also ordinary terrain, so in a dirt-heavy area the closest 50 matches can all be buried ground with the two actual marker stacks never in the running. `radius` still defaults to 64 as planned.
- **Cutting and filling run as two separate `PlanExecutor` passes** (not visible from the outside, but worth recording): a single combined plan would refuse up front with `missing_materials` for fill blocks the cut has not produced yet, since the executor checks what is carried once, before anything runs. Cutting first, then building the fill plan from what the cut actually gained, is what makes "little or nothing needs fetching" true.

Original plan:

Preparing a plot for building: "get me a clean field for building, 20x10, on the level I am standing on." Building, farming (a crop field, a pen), and railways all need flat, clear ground, and doing it by hand block by block is slow. This is the excavation machinery (break and place steps, the hazard rule, spoil handling) pointed at a *surface* instead of a hole: cut what is above the level, fill what is below it, clear what grows there.

- Branch: `feature/site-leveling`. Clients of the construction engine (`WorkPlan`, `PlanExecutor`, `SiteSafety`, `HazardRule`) and of the excavation supplies (`SupplyCrafter`, `SpoilDiscarder`, spoil policy); no new engine code is expected. Two small additions outside the engine: the player lookup (`EntityScanner`) also reports the player's facing (yaw), and `MarkerFinder` reads blocks through `BlockScanner`.

- **Parameters** (all numbers, like excavation: the agent extracts them from the request and the preview echoes what it understood):
  - **the area, three ways, in this order of priority:**
    1. **`width` and `length` given:** the rectangle starts **at the block the player stands on and extends the way the player is facing**: `length` blocks straight ahead and `width` blocks to the player's right, both read from the player's own position and view direction in the game (the yaw snapped to the nearest of the four directions, so the plot is always aligned with the world grid), not from the bot's position and no fixed compass direction. The player is the owner (`MC_OWNER`) or the player named in `for_player`. An explicit `origin` and `direction` still override this. The preview echoes the bounds, the direction it read, and the player's position it used, so a wrong reading shows before anything changes.
    2. **Corner markers (no size given):** the player marks the plot themselves by **placing two vertical stacks, each two blocks high, of dirt or cobblestone at opposite corners of the rectangle** (`marker_block` limits it to one of the two; both are accepted by default). The rectangle is the axis-aligned box between the two stacks, corners included. `MarkerFinder` looks for them near the player (default within 64 blocks) and takes only stacks that are **exactly two high, on solid ground, with air above and on all four sides at both heights**, so ordinary terrain (a dirt slope, a cobblestone wall) is not mistaken for a marker.   - `clear_height` (how far above the level is cleared, default 6, so a house fits; up to 24), `fill_block` (default: the cheapest block that the cut already produced, otherwise dirt), `surface_block` (optional, for the top layer, for example `stone` or `dirt`; grass cannot be placed by hand, so the natural top of an uncut area is left as it is), `margin` (extra cleared blocks around the rectangle, default 0), `clear_trees` (default true: logs and leaves above the level go, saplings and apples are picked up), `max_fill_depth` (default 6, how deep a hole may be filled), and `spoil_policy` and `on_inventory_full` as in excavation.
- **What `auto` level means.** The level is the height the plot ends at, and it decides how much work there is. `here` uses the height under the player's feet, which is the right answer when the ground is flat but a poor one on a slope or a hill: standing on a mound 4 blocks above the rest of a 20x10 plot would mean filling roughly 200 columns four blocks deep. `auto` surveys the height of every column in the rectangle and proposes the height that moves the fewest blocks in total (the median of the heights, which minimises the sum of the differences): most of the ground stays as it is, the mound is cut, the pit is filled. It is a **proposal, not an action**: `preview_flatten` shows the cost at the player's level next to the cost at the suggested one (blocks to cut, to fill, and to fetch), and the agent tells the player ("here would need about 800 blocks of fill, level 64 needs 40 cut and 20 fill; which do you want?") and then calls with an explicit `y`. Without the player asking for it, the level stays `here`.
- **What it does** (one plan, run by the executor, so it inherits resume, protection, and safety):
  - **Survey first.** The preview reads the surface height of every column: lowest, highest, median, how many columns need cutting and how many need filling, and the block counts: cut, fill, and the fill that the cut can supply.
  - **Cut and fill balance.** Cutting is done first, top layer down, and what it yields (dirt, stone, sand, gravel) is reused as fill, so the plot needs few or no materials from outside. Only the shortfall is fetched (`fetch_from_storage`) or reported as `missing_materials` with exact numbers, and a surplus follows the spoil policy.
  - **Clearing.** Everything natural above the level in the rectangle and the margin: grass, flowers, snow layers, dead bushes, vines, leaves, trunks (with `clear_trees`), and loose blocks. Order: top down, so nothing falls on the bot; sand and gravel overhead are broken from the side by the existing falling-blocks rule.
  - **Filling.** Support first, from the lowest cell up, each cell placed against a solid neighbour. Holes deeper than `max_fill_depth` are not filled (`too_deep`, with the place), so an open cave under the plot is never buried by accident. Shallow water is filled with blocks; flowing water that comes back is reported.
  - **Safety, all from what already exists.** Lava in or next to the rectangle refuses (`unsafe_site`); the hazard rule ends a chain at an unexpected cavity, spawner, or player-made block; protected areas are refused whole (`protected_area`); **blocks a player placed** (planks, fences, chests, doors, anything not natural terrain) inside the rectangle are never removed by default: they are reported as `blocked_cells` and the preview lists them, and only an explicit `clear_structures: true` from the player's request removes them. Nothing outside the rectangle and the margin is ever changed.
  - **Result** carries the bounds, the level, cut, fill, and cleared counts, what was gained or used, what was left (with reasons), and a hint: the `origin` and `level` are what `build` or `build_farm` should be given next. An optional `label` saves the plot as a landmark (`set_landmark`) so "build on the plot" resolves later.
- **Limits:** 1 to 64 blocks per side (4096 columns at most). A larger job is several calls.
- **Other features use it:** the crop field and the pen from farming and railway grading call the same plan builder for their ground; nothing here depends on them.
- **Tests:**
  - unit: the surface survey and the cut and fill counts over a fake height map (flat, hill, hole, slope, tree), area from the player's position and facing (each of the four directions, width to the right, an explicit origin overriding it), `MarkerFinder` (a valid pair, one or none, three and the nearest pair, stacks that are one or three high or attached to terrain are ignored, dirt and cobblestone, size limit, the markers removed and picked up), `level` resolution (`here`, `y`, `markers`, and `auto` only suggests, the suggested level being the median), the cut and fill balance and the shortfall, `max_fill_depth`, margin, `clear_trees` on and off, ordering (top down for cuts, bottom up for fills), refusals (lava, protected area, player-made blocks unless `clear_structures`), size limits, and preview equal to what the run does
  - integration: `flatten_area` through the tool layer on a stateful fake world: uneven ground ends flat at the level, cut soil is reused as fill, an interrupted run continues where it stopped, nothing outside the rectangle changes
  - e2e: uneven ground prepared over RCON (a hill, a hole, a tree, flowers, a shallow pond): `flatten_area` 20x10 at the bot's level leaves every top block at the level and air above it up to the clear height, and a strip outside the rectangle is untouched (checked through RCON); the owner bot faces each direction in turn and the rectangle follows; two dirt stacks placed at opposite corners define a plot with no size given, and they are gone afterwards; a player-placed wall inside is not removed; lava beside the area refuses; `preview_flatten` changes no block
- **Exit criteria:** "get me a clean field for building, 20x10, on the level I am standing on" leaves a flat, cleared 20x10 plot starting where the player stands and running the way they face, at that level; "level the plot between my two markers" does the same for the marked rectangle; neither touches anything outside the plot or anything else a player built, and the reply says the bounds and level to build on.

#### Dug rooms (`feature/dug-rooms`, done)

"Dig a room 5x5x4 behind this wall": the player and the bot walk to a hill, a mountain wall, or a cave wall, and the player looks at the wall and asks for a room. This is a new **shape in the excavation registry** (`room`, a new `ExcavationProvider`; no engine changes), used through `excavate` and `preview_excavation`. What is new is reading the wall the player looks at, the entrance, and the door.

- **Which wall ("this wall").** `WallTarget` reads what the **player is looking at**: the block under the crosshair and the **face** that was hit (the `LookTarget` port gains the hit face). The room is dug **into** the wall, along the direction opposite to the face's normal, so it goes straight into the rock the player is looking at. Only horizontal faces count: a look at the floor or the ceiling fails with `not_a_wall` and asks the player to look at a wall. The entrance column is the hit block's column; its floor is the walkable floor in front of the wall (found by scanning down the column in front of the face, with the player's own standing level as the fallback), so the entrance is at floor level and the player can walk in, whatever height they were looking at. Without a usable look (nothing under the crosshair within reach), or when the request names them, explicit `at` (the wall block) and `direction` are used; otherwise it asks. The player is the owner or `for_player`.
- **Parameters** (numbers, as everywhere in excavation; the preview echoes them): `width` (across, 2 to 24), `length` (deep, 2 to 24), `height` (2 to 8; for example 5x5x4), `entrance` (`dig`, the default; `player`; `none`), `entrance_length` (blocks of wall dug through before the room begins, default 1), `entrance_height` (default 2) and `entrance_width` (default 1, up to 3), `door` (an item name such as `oak_door`, or `true` for the best door carried or craftable; **one door per cell across the entrance**, so a 2-wide entrance gets two doors and a 3-wide one three), `entrance_at` (`center`, the default, `left`, or `right`: where the entrance sits along the room's front wall, as seen entering the room; `left` and `right` put it **against the left or right edge** of the wall, so its outer cell is the first or last cell of the front row, at any room width and with any entrance width), and the usual `torch_spacing`, `min_light`, `spoil_policy`, and `on_inventory_full`.
- **The entrance.** **By default the bot digs a 1 wide, 2 high entrance** from the face of the wall, `entrance_length` blocks deep and centred on the room's front (with an even room width and an odd entrance width there is no single middle cell: the entrance takes the left of the two middle cells, as seen entering the room; "the entrance on the left (or right) edge" is `entrance_at: left` (or `right`)); the room begins right behind it. The player's words change it: "I will dig you an entrance" is `entrance: player`, where the bot digs only the room and, before it starts, **asks and waits** (`waiting_for_input`, a `needs_decision` event) until the entrance cells are open, then goes on when the player answers `resume_task`; "the room only" or a hole already there is `entrance: none`, and the room starts at the first cell that is open; a bigger opening is `entrance_width` and `entrance_height`.
- **The door.** "Put a door here on finish" is `door`: at the end, when everything else is done, real doors are placed in the entrance, **one in each cell across its width** (so "a 2x2 entrance with doors" gets two doors, which the game joins into a double door, hinges on the outer sides; a 3-wide entrance gets three). They go in last, like the house door, turned to lie in the plane of the wall with `alignAxis`, on the entrance floor, in the outermost row of cells. A door is two blocks high, so with `entrance_height` above 2 the cells above the doors stay open and the preview warns about the gap; with a height of 2 (the default and the "2x2" case) they fit exactly. The number of doors is counted in the preview's `needs`. The door is fetched from the inventory or storage, or crafted from planks by the supplies crafter when the materials are there; otherwise the result says exactly what is missing and the room is still finished.
- **Light.** As in tunnels and quarries: `light` steps with `torch_spacing` (default 6, 0 for none) and `min_light` (default 7). In a room the torches go on the **floor along the walls** so the middle stays free; with none carried, torches are crafted (`no_torches` behaviour of the excavation extras); a lit room is checked against the light level, so a room that is already bright gets none.
- **How it is dug.** One plan of `break` steps: the entrance cells first, then the room **layer by layer from the entrance inwards**, each cell needing the one before it (nothing is dug through rock from a distance), the bot standing inside. The whole excavation safety set applies unchanged: `HazardRule` (lava or water next to a cell ends that chain, an open cavity that the dig did not make itself ends it as `cave_breakthrough`, the entrance direction being left out of the probes, sand and gravel overhead, spawners, chests and other player-made blocks), protected areas refused whole, ore touching the room mined as a vein (`veins`), spoil by the storage policy, resume by re-running. A wall of **player-built blocks** is refused (`player_block`), as always.
- **Tests:**
  - unit: `WallTarget` (each horizontal face gives the direction opposite to the normal, floor and ceiling rejected, the entrance floor found in front of the wall, explicit `at` and `direction`), `RoomProvider` (the entrance and room cells for odd and even widths (and `entrance_at` `left` and `right` against each edge, with 1, 2, and 3 wide entrances), entrance length, height, and width overrides, each `entrance` mode, the door step last, torch cells along the walls, limits, cell `needs` order, the probe list leaving out the entrance direction), the `entrance: player` wait and resume, the door fetch, craft, and shortfall paths (one door for a 1-wide entrance, two for 2 wide, the count in `needs`, the gap warning for an entrance taller than 2), and preview counts equal to what the run does
  - integration: `excavate` with `shape: room` through the tool layer on a stateful fake world with a stone wall and a fake look target: entrance, room, door, and torches come out as planned; a cave behind the wall ends the dig with the reason; an interrupted run continues where it stopped
  - e2e: a solid stone hill built over RCON, the owner bot made to look at its wall (`world.face`): a 5x5x4 room with a 1x2 entrance and an oak door (and a 2x2 entrance with two doors), torches placed in the dark, and every cell checked through RCON; `entrance: player` waits, then continues after the entrance is cut by hand; water or lava behind the wall stops the dig one block short
- **Exit criteria:** after "follow me" to a hill and "dig a room 5x5x4 behind this wall", the bot digs a 1x2 entrance into the wall the player is looking at and a lit 5x5x4 room behind it, and with "put a door here on finish" ends by hanging a door in the entrance; "I will dig you an entrance" makes it wait for the player instead of digging one.

#### Opening ordinary doors (`feature/door-opening`, done)

Today a closed door is a wall for the bot: the movement library's door option is off (its own comment says it "causes issues", probably on servers other than Paper), so `goto` into a house with a closed wooden door fails as unreachable or stuck, and the bot cannot leave a room whose door it (or the player) closed. This makes ordinary doors work; **iron doors and buttons are the next phase.**

- **Which blocks.** Wooden doors (`*_door` except iron), fence gates (`*_fence_gate`), and wooden trapdoors (`*_trapdoor` except iron), by a table in one place; anything else that is openable is left alone. An iron door or iron trapdoor is not handled here: navigation reports the reason `needs_switch` (the next phase deals with it) instead of trying.
- **How, and the risk.** First a spike with a Docker e2e: turn on the library's own door handling in the safe movement profile and see whether it is reliable. If it is not, the bot handles doors itself in `NavigationRunner`: when the route ends at a closed openable block, or the bot is stuck right beside one, it opens it (a right click on the block), walks through, and continues. Either way the result is the same to the tools: `goto`, `follow_player`, and every task that walks can go through doors.
- **Close behind.** After passing, the bot **closes the door or gate behind it** (default `close_doors: true`, also settable as a standing instruction), so animals do not get out of pens, monsters do not get into houses, and a house is not left open. A fence gate of a registered pen is always closed again. A door that was already open is left open, and one that cannot be closed (something in the doorway) is reported.
- **Never through a locked way.** A door that will not open after two tries ends the walk as `door_stuck` with the place; the bot does not break doors down.
- **Tests:**
  - unit: the openable-block table (wooden doors, gates, trapdoors yes; iron no), open state read from the block, the open-pass-close sequence, closing behind only what it opened, a stuck door, `needs_switch` for iron, `close_doors: false`
  - integration: `goto` into a room behind a closed door on a stateful fake world: the door is open while passing and closed afterwards
  - e2e: a small house with a closed oak door: `goto` inside and back out, the door is closed after each pass (checked through RCON); a fence-gate pen: the bot passes and the gate is closed again; an iron door built over RCON: `goto` reports `needs_switch`
- **Exit criteria:** "go inside the house" through a closed wooden door works and leaves the door closed; an iron door is reported, not attempted.

### Phase 17: Iron doors and switches (¾ session)

An iron door cannot be opened by hand. It opens while something powers it: a button, a lever, or a pressure plate, usually beside the door. The bot cannot see the redstone behind them, so this phase recognises switches by where they are and checks by trying. It follows Phase 15's ordinary door opening.

- Branch: `feature/switches`. Reuses the door handling and `NavigationRunner` of Phase 16, and `LookTarget` for "the button I am looking at".
- **Tools:**
  - `press_switch`: press a button, toggle a lever, or step onto a plate at `at`, or the one the player looks at; the result says what happened to the door beside it, if any.
  - `open_door`: open a door, ordinary or iron, by position or the one the player looks at, optionally walking through (`walk_through`) and closing or restoring things behind (`restore`, default true). For an iron door it finds and tries the switches itself (below).
  - `find_switches`: read-only, lists the buttons, levers, and plates around a door or a position, with their kind and distance.
- **`SwitchFinder`.** Around a closed iron door, within about 4 blocks and on the side the bot is on, it lists buttons (wood and stone), levers, and pressure plates, nearest first, with the wall or floor each is on. It cannot know the wiring, so it is a **ranked guess that is verified**: press the best candidate, watch whether the door's `open` state changes, and if not, try the next one, at most 4 candidates and 2 rounds. A door that stays shut is reported as `door_did_not_open` with what was tried.
- **Timing.** A stone button holds the door open for about 1 second, a wooden one for 1.5 seconds, a lever until it is toggled back, and a plate while somebody stands on it. So `open_door` stands where both the switch and the door are within reach, presses, and **walks through at once** (`DoorPasser`); for a lever it goes through and then puts the lever back to how it was found (`restore`), so a house is not left open. A pressure plate in front of a door opens as the bot walks on it; the route does not avoid plates that lead to a door.
- **Safety.** Buttons and levers can also fire dispensers, pistons, TNT, or traps, and the bot cannot tell. So: **a `SwitchPolicy` standing instruction** (`ask`, the default, `auto`, `never`, mirrored as a standing instruction like the other policies): with `ask`, a walk that meets an iron door fails with `iron_door_blocked` and the switches found, and the agent asks the player before `open_door`; with `auto` the bot tries the switches beside the door it needs by itself; with `never` it does not. Only switches **within 4 blocks of the door** are ever tried on its own; anything else needs the player to point at it or give its position. It never presses switches in a protected area's machinery unless the player names them, and it stops after the limits above. A pressed switch that seems to have done something else (blocks changed around, an explosion) ends the attempt and is reported.
- **Navigation.** `goto` and the other walks report `iron_door_blocked` (with the candidates) instead of `needs_switch` when the policy is `ask`, and go through by themselves when it is `auto`.
- **Tests:**
  - unit: `SwitchFinder` (each kind, ranking, ignoring far or wrong-side switches), the press-verify-next loop and its limits, timing per button kind, the walk-through window, lever restore, `SwitchPolicy` (`ask`, `auto`, `never`), refusals, and `find_switches` changing nothing
  - integration: `open_door` and `goto` through an iron door on a stateful fake world with a button and a lever
  - e2e: an iron door with a stone button on the frame block beside it (over RCON): `open_door` with `walk_through` gets the bot in before the door closes; a lever door is left as it was found; a door with a decoy button that does nothing tries the next candidate; `find_switches` lists them; with policy `ask` `goto` reports `iron_door_blocked`
- **Exit criteria:** "get into the house" through an iron door with a button beside it asks (or, with the standing instruction `auto`, simply does it), presses the button, walks in, and leaves the house as it was (a lever put back); a door that does not react is reported with what was tried.

### Phase 18: Farming, crops, animals, and trees (3.25 sessions)

Hunting takes animals from the world and never adds any, and food stops when the wild herds run out; gathering fells trees and never plants them. Farming closes those loops: grow crops, breed animals, plant forests, keep a steady supply.

**Design decision: layout is building, tending is not.** A vegetable garden or a pen *is* a buildable structure, so laying one out belongs to the construction engine (a new `PlanProvider`, executed by `PlanExecutor`, with `SiteSafety` and `LightManager`). But planting, harvesting, replanting, and breeding are recurring operations on *whatever farm exists*, including one the player built by hand, so they are ordinary skills with no dependency on the engine. Merging them into "building" would make every harvest a build plan; keeping them apart lets the tending skills work on the player's own farms and on ones the bot built.

- Branches: `feature/crop-farming` (layout provider and crop tending), then `feature/animal-farming` (pens, luring wild animals in, and breeding), then `feature/tree-farming` (groves and replanting). Start after the construction engine; the tending skills themselves do not need it and could go earlier if wanted. Two follow-ups after the three: `feature/sapling-collecting` (getting saplings by breaking leaves, on request) and `feature/discover-farm`.
- **Farm layout (engine clients):**
  - `CropFieldProvider`: parameters `width`, `length`, crop type. Tilled plots with a water channel so every plot is within 4 blocks of water, a fence with a gate, torches for light, optionally a chest and a composter. Needs a hoe and seeds; the plan preview lists what is missing. Tool: `build_farm` with `kind: field`.
  - `AnimalPenProvider`: fenced pen with a gate, sized for the species and herd (`entity cramming` limits the animals per block), water optional. `build_farm` with `kind: pen`.
  - `FarmRegistry` (persisted per world, like the container index): registered farms (built by the bot or pointed out by the player: position, size, crop or species). Farms are protected from `collect_block` by default; `list_farms`, `register_farm`.
- **Farm groups: "our farm" is several components** (a cow pen, a chicken pen, a pig pen, and several fields, each fenced apart). Each component is its own `FarmRegistry` entry, and entries can share a **group** (`register_farm` takes `group`, for example `home`; a group can be tied to a landmark or an area, so "the farm near home" resolves to it). Groups are a label over entries, not a new structure, so components can still be tended one by one, and a component can be built by the bot or by the player.
  - **`tend_farm` takes a group** and runs its components in a fixed order (crops first, then animals, with eggs collected for each pen), each under the same safety checks, with one time limit for the whole pass. A component that fails or is blocked is reported and skipped; the others carry on. The result is **one summary with a breakdown per component** (for example: wheat field 2 harvested and replanted, cow pen at 8 adults and 2 calves, chicken pen eggs 6 stored and 54 thrown, pig pen fence gap at x, y, z).
  - **`inspect_farm` is read-only** ("go check our farm"): for a group or one component it reports without touching anything: crops by ripe, growing, and empty plots; animals by species, adults, and babies against the herd target and capacity; eggs lying around; feed and seeds carried; and problems (a gap in a fence or an open gate, no water within 4 blocks of a plot, trampled farmland, light too low, a dead or missing animal count). "Check" means this tool first; `tend_farm` is for "do the work".
  - **`discover_farm`** scans around a position or landmark for fenced areas (`PenDetector`) and farmland, works out what each one is (species by the animals inside, crop by the plants), and **proposes** a grouped registration; nothing is registered until the agent (after the player agrees) calls `register_farm`. Player-built farms therefore need no description piece by piece. Nothing in it is ever broken or changed. As built (`feature/discover-farm`): fields (crop by what grows on the farmland) and pens (species by the animals inside; an empty fenced area with a gate is a low-confidence proposal) are proposed, each with the exact `register_farm` arguments, a free label, and the requested `group`; what a registered farm already covers is listed as `alreadyRegistered`; groves are not detected, and the `PenDetector` idea became fence blocks plus a flood fill (`findEnclosures`), since a pen is found from the fence rather than from an animal.
- **Crop tending (plain skills):**
  - `PlantCropsSkill`: hoe dirt and grass into farmland, plant seeds, carrots, potatoes, or beetroot on free farmland (wheat, carrots, potatoes, beetroot first). Never jumps or walks over farmland (trampling turns it to dirt): the standing spots are the paths and the field edge.
  - `HarvestCropsSkill`: only harvests fully grown crops (the block's age is at maximum), replants at once, and keeps enough seeds for the next round. Optional bone meal on young crops. Yield goes through the storage policy.
  - `TendFarmSkill`: one pass over a registered farm (harvest, replant, breed) with a time limit, so "keep the farm running" is a repeatable task.
- **Stocking a pen** (a plain skill, like tending: it walks up to whatever animals are actually out there and needs no engine involvement, only a pen that already exists — the bot's own or one the player built):
  - `LureAnimalsSkill` (`lure_animals`): given a species, a count, and where to put them (a registered farm component, or a position), finds nearby wild animals of that species with `AnimalScanner` (never tamed, named, saddled, or ridden — the same exclusions `hunt_animals` respects, since a lured animal that turns out to be someone's pet is exactly the kind of thing this project never does without being asked), equips the item that species follows (the same table `BreedAnimalsSkill` uses below), and walks it in: gets within the vanilla follow range (about 10 blocks) holding the item, then advances toward the pen's gate in short hops, so the animal keeps re-triggering its own follow behaviour, checking after each hop that it is still close enough to be following. The gate itself needs no special handling: walking through it is an ordinary `goto`, and the fence gate is already opened and closed behind the bot by the door-opening machinery from Phase 16.
  - **An animal that stops following is not chased.** If it falls behind, loses interest, or drops out of view after a few hops, that one is abandoned (recorded, not retried) and the next nearest candidate is tried, up to `count` led in or the search area exhausted. The result reports how many were led in against how many were asked for, and why each abandoned one was left behind (`lost_interest`, `unreachable`).
  - Stops with `no_animals_nearby` when nothing of the species is found within the search radius, and reports `pen_full` (a shortfall, not a failure, the same as a `give_items` shortfall) once the destination pen already holds the herd size `entity cramming` allows.
- **Animal breeding (plain skills):**
  - `BreedAnimalsSkill`: feed pairs of adults of a species the right food (wheat for cows, sheep, and mooshrooms; carrots, potatoes, or beetroot for pigs; seeds for chickens; carrots for rabbits), waits for the babies, respects the 5-minute breeding cooldown and the 20-minute growing time, and never breeds tamed, named, or ridden animals. It stops at the pen's capacity or the requested herd size.
  - `HerdManager`: keeps a herd at a target size by breeding up and by culling the surplus with `hunt_animals`, which keeps its breeding floor of two adults. Reuses `PenDetector` and the animal catalog.
- **Eggs** (in `feature/animal-farming`, after breeding; chickens lay an egg every 5 to 10 minutes, so a chicken pen produces them all the time and they lie on the ground until somebody picks them up):
  - `CollectEggsSkill` (`collect_eggs`): picks up the `egg` items lying in a registered pen or a given area (`DropCollector`, so it also skips what the bot threw away on purpose), never inside a protected area that is not the pen, and never by hitting or harming a chicken. Also run as a part of a `tend_farm` pass over a pen.
  - **Default split: 10% is stored, 90% is released for chicks.** Storing goes through the storage rules and policy like every other deposit (`ContainerSelector`; a rule for `egg` picks the chest, otherwise any chest with room); the stored share is rounded up, so with any eggs at all at least one is kept. The rest is **thrown into the pen** (`EggThrower`, a client of the `Gaze` and `WindowDropper` ideas: the bot stands at the gate or the fence, faces a free cell inside the pen, and uses the egg from the hand, one at a time with a short pause; a thrown egg hatches with a 1 in 8 chance, and on a hatch 1 time in 32 gives four chicks, so about one chick per eight eggs; thrown eggs land anywhere in the pen and never near a player).
  - **Per call or as a standing instruction the split can change:** `store_fraction` (0 to 1, default 0.1) and `release` (`hatch`, the default, or `store`, which keeps everything). `set_egg_policy` saves the standing answer per world (`EggPolicy`, mirrored as the standing instruction `egg_policy` so the briefing shows it), like `FoodPolicy`. An instruction from the player always wins over the default.
  - **One safety exception to "release the rest":** chicks count against the pen (`entity cramming` and the herd size), so the release stops when the pen already holds its target number of chickens (`max_chickens`, the herd size given to `breed_animals` or the pen's capacity); the eggs that were not thrown go into storage and the result says so (`released`, `stored`, `pen_full`). A player who wants more chickens than that says so.
  - Tools: `collect_eggs` (area or farm, `store_fraction`, `release`, and `max_chickens`), `set_egg_policy`; the numbers stored, thrown, and picked up are in the result.
- **Tree farming** ("plant a forest of 10 trees around our house"):
  - `TreeGroveProvider` (an engine client): turns "N trees" plus an area (around a position, a landmark, a protected area, or a registered structure; `around` a house means a ring at a distance) into sapling positions on dirt or grass. It keeps the spacing each species needs to grow (light and free space above, at least 2 blocks between oaks and birches, a 2×2 spot for spruce, jungle, and dark oak that only grow big from four saplings), keeps clear of doors, paths, and farms, and previews the positions before anything is placed. Tool: `plant_trees` (`species`, `count`, and an area).
  - Saplings come from the inventory; when short, `plant_trees` says how many are missing and does not go looking (see sapling collecting below). Bone meal speeds growth when the bot has some and the request says so.
  - `TendGroveSkill`: a pass over a registered grove: replants a sapling where a tree was felled (also after `collect_block` on logs, when the grove is registered), clears trees that grew wrongly, and reports growth. Groves are registered in the `FarmRegistry` like fields and pens, so a grove is not cut down by accident: felling from a registered grove is a deliberate `harvest_trees` call that replants.
  - Tools: `plant_trees`, `harvest_trees`, and the grove shows in `list_farms`.
- **Sapling collecting** (`feature/sapling-collecting`, a follow-up after tree farming; **optional and on request only**: nothing plants trees or gathers wood and goes looking for saplings by itself, the player asks for it in chat, for example "get me 10 oak saplings" or "chop 20 logs and bring some saplings too"):
  - Saplings drop by chance when **leaves are broken by hand or with a tool** (about 1 leaf in 20 for oak, birch, spruce, acacia, dark oak, and cherry; about 1 in 40 for jungle), so the goal is counted in saplings and the work is a budget of leaves. **Never with shears**: they make the leaf block itself drop and no sapling (`chooseTool` never picks them, and a test pins that). Leaves that decay after a tree is felled also drop saplings on the ground, so the skill first picks up saplings already lying nearby.
  - `CollectSaplingsSkill` (`collect_saplings`: `species` (any when left out), `count`, `max_leaves` (default 40 per sapling wanted, at most 1000), `max_distance`, `on_inventory_full`): a client of `CollectBlocksSkill` (so protected areas, lava, no tunnelling, and the full-inventory policy apply unchanged), which it calls in small batches of the species' own leaves (`oak_leaves` gives `oak_sapling`), counting the saplings gained after each batch. Stops when the count is reached, the leaf budget is spent (`leaf_budget`), or no more leaves are found or reachable (`no_leaves`, or the reason `collect_block` gave). The result gives saplings gained, leaves broken, and what else the inventory gained (sticks, apples).
  - **As a part of gathering wood:** `collect_block` takes an optional `saplings` count. After the logs are done it collects that many more saplings of the same species (from `oak_log` the oak saplings; from a group such as `logs`, any species), counting the ones the logs run already gained. Running out of leaves does not fail the logs: the result carries a `saplings` section (`gained`, `requested`, `leaves`, `stoppedBecause`).
  - Not planned: bone meal on leaves, or waiting around for leaves to decay.
- Tools: `build_farm`, `plant_crops`, `harvest_crops`, `lure_animals`, `breed_animals`, `collect_eggs`, `set_egg_policy`, `tend_farm`, `inspect_farm`, `discover_farm`, `plant_trees`, `harvest_trees`, `collect_saplings`, `list_farms`, `register_farm`.
- Safety and rules: farms are protected areas for other tasks; lighting and water are checked before planting; night work follows the threat policy; a tool that would trample farmland fails with a typed reason.
- **Tests:**
  - unit: `CropFieldProvider` (plot and water layout, every plot within 4 blocks of water, gate, materials), crop age reading, `HarvestCropsSkill` (mature only, replant, seed reserve), `PlantCropsSkill` (hoeing, free plots, no trampling), `LureAnimalsSkill` (right food per species, tamed/named/saddled/ridden excluded, an animal that stops following is abandoned and the next tried, stopping at the requested count, `no_animals_nearby`, `pen_full` as a shortfall not a failure), `BreedAnimalsSkill` (right food per species, cooldowns, floor, protected animals, capacity), `HerdManager` (breed up, cull down), `FarmRegistry`, `TreeGroveProvider` (ring around a structure, species spacing, 2×2 spots, avoided cells, sapling count and shortfall), `TendGroveSkill` (replant, wrongly placed trees), `CollectSaplingsSkill` (only the wanted species counted, the leaf budget, ground saplings first, never shears) and the `saplings` option of `collect_block`, `CollectEggsSkill` (only eggs in the pen, the 10% share rounded up and at least one, the `store_fraction` and `release` overrides, the standing policy, no throwing when the pen is full, no chest space falls back to asking), `EggThrower` (aims at a free cell inside the pen, one egg at a time, stops on abort), `EggPolicy`, farm groups in `FarmRegistry` (grouping, resolving "the farm near home", a component in one group at a time or several), `tend_farm` on a group (order, one failing component does not stop the rest, the shared time limit, one summary), `inspect_farm` (each kind of finding, changes nothing), `discover_farm` (fenced areas and fields found, species and crop inferred, proposals only)
  - integration: `build_farm` through the tool layer on a stateful fake world produces the expected block grid; plant, grow (fake time), harvest, and replant cycle; lure a set of wild animals from open ground into a registered pen, gate closed behind; breed to a target herd size; plant a small grove around a spot and check the saplings' positions, replant after felling
  - e2e: a small farm with a cow pen, a chicken pen, and a wheat field: `discover_farm` proposes all three; after registering them as one group, `inspect_farm` reports the ripe and growing counts and the animal counts without changing a block, and `tend_farm` on the group harvests and replants the field, collects the eggs, and returns one summary with three parts; a gap cut into a fence shows up as a problem in `inspect_farm`; eggs summoned as items in a fenced pen with chickens: `collect_eggs` picks them all up, stores exactly 10% (rounded up) in a chest and throws the rest (the chest count is exact; with 64 eggs at least one chick appears, the chance of none being under 0.03%); `store_fraction: 1` stores everything; a full pen throws nothing; `build_farm` lays out a small field on flat ground and the block layout checks out through RCON; seeds planted, crops advanced with `/data merge` or bone meal, harvested and replanted; wild cows summoned outside an empty pen are led in by `lure_animals` and the gate is closed behind them, then two of them fed wheat produce a calf; a pen is built and a herd bred up to its size; saplings planted around a point with the right spacing and grown with bone meal
- **Exit criteria:** "make me a wheat farm here" builds a watered, fenced, lit field and plants it; "harvest the farm" harvests only what is ripe and replants; "round up 4 wild cows into the pen" leads them in one at a time, skipping any that wander off, and reports the count against what was asked; "breed the cows up to 8" feeds pairs until the herd has 8 adults, without ever touching pets or the last breeding pair; "go check our farm near home" answers with one report over every pen and field of the group without changing anything, and "run the farm" tends all of them with one summary; "collect the eggs" stores a tenth in a chest and throws the rest into the pen for chicks (unless told otherwise or the pen is full); "plant a forest of 10 trees around the house" places 10 saplings with room to grow, and felling them later replants; "get me 10 oak saplings" breaks oak leaves until it has them or says why it stopped, and "chop 20 logs and bring some saplings too" does both and reports each.

### Phase 19: Railways (2 sessions)

- Branch: `feature/railways`. Built on the construction engine, excavation (for underground lines), and lighting; materials come from the inventory or storage.
- **Route planning** (`RailRoutePlanner`): from a start to an end (coordinates, a player, or a landmark), as a chain of straight runs with 90° turns, staying within rail rules: slopes of one block up or down per rail, curves only with plain rails (powered rails cannot bend), no water or lava on the route. `layout`: `surface` (the line follows the terrain: gaps and dips are filled with support blocks, small rises are cut, water and ravines are bridged), `underground` (a tunnel dug by the excavation engine, lit, for a metro), or `auto` (surface where it is easy, underground where the terrain is not). A preview reports length, materials, and problems before anything is built.
- **Two variants:**
  - `economy`: plain rails, with a **powered rail every `spacing` blocks on level track (default 8; 7 to 10 allowed) and every 3 blocks on slopes**, each fed by its own redstone torch.
  - `rich`: powered rails all the way, for the best speed. Power passes from one powered rail to the next up to 8 rails away, so a redstone torch is needed about every 9 rails, not one per rail.
  - Both place a torch or redstone block for power next to each powered rail in a way that has to be verified in the game (the power layout is chosen by an e2e run: a minecart must actually accelerate along the test line).
- **Materials** (worked out by the planner and the recipe book): rails (6 iron ingots and a stick make 16), powered rails (6 gold ingots, a stick, and redstone make 6), redstone torches (redstone and a stick), minecarts (5 iron ingots), support blocks. A shortage is reported per item, with the offer to gather, smelt, or fetch it.
- **Trolley:** `place_minecart` puts a minecart on a rail (by default at the start of the line); riding it is up to you.
- **Verification:** after laying, the bot walks the line and checks every rail's presence, orientation, and powered state, and re-lays what is wrong.
- **As built** (`feature/railways`, details in AGENTS.md): the power layout was chosen by a real-server experiment, as the plan asked: a redstone torch **beside** a powered rail powers it, a block behind a powered first rail starts a resting cart, and plain rails alone stop a cart within about 10 blocks. The first rails of a line are therefore a powered **run of four** (a single powered rail every 8 left a cart that started from rest stranded 2 blocks in). `auto` picks surface or tunnel for the whole line, not per stretch. The engine gained `passable` and `clearedFirst` place steps and `standing: 'inside'` use for a tunnel.
- Tools: `plan_railway` (dry run), `build_railway`, `place_minecart`.
- **Tests:**
  - unit: route planning on synthetic terrain (slopes, turns, gaps, water, obstacles; `surface` versus `underground`), spacing rules for both variants (level and sloped runs), rail orientation at corners and slopes, material calculation, verification
  - integration: `build_railway` through the tool layer on a grid-based fake world, including a tunnel section
  - e2e: a surface line on flat ground and one that climbs a hill, both variants, verified through RCON block by block; a minecart placed at the start and pushed goes the whole way (speed checked); an underground line through a tunnel with torches; missing-materials report
- **Exit criteria:** "build a railway from here to the base, economy variant, and place a minecart" produces a working line (surface or underground) with the powered rails at the stated spacing, and the cart runs it.

### Phase 20: Sleeping and respawn point (1 session)

Two reasons to sleep: a bed sets the bot's respawn point (after a death it wakes up at home instead of at the far-away world spawn, which also makes drop recovery quicker and safer), and sleeping skips the night.

- Branch: `feature/sleeping`.
- **Rules the game imposes, which the feature must respect and explain:**
  - A bed only lets you sleep at night (from about 12,540 to 23,460 ticks) or during a thunderstorm; by day, using a bed only sets the respawn point ("Respawn point set", read from the chat line).
  - **In multiplayer the night is skipped only when enough players sleep** (`playersSleepingPercentage`, default 100%): the bot sleeping alone does not skip the night while you are awake, and a second player counts. The result must say so. Lowering the percentage or setting the time are server commands and only happen on your request, when the commands feature makes them available.
  - Sleeping is refused when hostile mobs are near ("monsters nearby": about 8 blocks around, 5 up and down), and the bed is the respawn point only while it exists and is not obstructed; otherwise the game silently falls back to the world spawn.
  - **A bed explodes in the Nether and the End.** The bot never sleeps or sets a respawn point there (`wrong_dimension`, a hard guard, not a setting).
- **`Sleeper` port** (`sleep(bed)`, `wake()`, `isSleeping()`; Mineflayer `sleep`, `wake`, and the `sleep` and `wake` events). Reflexes wake the bot before they act: a sleeping bot cannot flee or fight, so `ThreatResponse` and the others call `wake()` first (with a unit test for it), and a hit wakes it anyway.
- **`BedRegistry`** (persisted per world): known beds and which one is the respawn point (position, colour, when it was set, whether it was seen to be intact). After a death the bot notices when it did not respawn at the bed (destroyed or blocked) and tells the agent so the record is corrected.
- **Skills:**
  - `SleepSkill` (`sleep`): find the nearest known or visible bed (or the one named), check dimension, time or storm, and monsters (with an offer to clear the area or light it), walk there, sleep, and stay until morning or until woken, reporting whether the night was skipped or is still going because another player is awake. Aborting or a threat wakes the bot.
  - `SetRespawnPointSkill` (`set_respawn_point`): use a bed by day or night, and confirm from the "Respawn point set" line; fails typed when it is not confirmed.
  - Beds are made with the existing tools: `craft` a bed (three wool and three planks) and place it. `PlaceBedSkill` puts it down on a free 2-block spot (the bed is two blocks, so it needs the free spot, not a single-cell `Placer` call). The building phase's shelter blueprint can include a bed and torches.
- **`SleepPolicy`** (standing instruction): `ask` (default: at nightfall the agent gets a `needs_decision` event and asks whether to go to bed), `when_idle` (the bot goes to bed by itself at night when no task is running and no threat is near), `never`. Nothing in this feature ever forces you to sleep or teleports you.
- Tools: `sleep`, `set_respawn_point`, `place_bed`, `list_beds`, `set_sleep_policy`.
- Relation to the backlog: "night shelter when far from a bed" (build or dig in) stays a separate item; this feature covers having a bed. The cave exploration feature can use `place_bed` and `set_respawn_point` for camps.
- **Tests:**
  - unit: `SleepSkill` against fakes (time window, storm, monsters near, wrong dimension, no bed, walking to the bed, woken by a threat or an abort, night skipped versus another player awake), `SetRespawnPointSkill` (confirmation line, timeout), `BedRegistry` (persistence, respawn point moves when another bed is used, lost-bed correction), `SleepPolicy`, the reflex waking the bot first, `PlaceBedSkill` (free spot search)
  - integration: `sleep` and `set_respawn_point` through the tool layer on a stateful fake world; a death respawns at the bed, and a destroyed bed is noticed and reported
  - e2e: at night the bot sleeps in a bed and the night is skipped when the server's sleeping percentage lets it; by day the respawn point is set and, after the bot is killed, it wakes up at the bed (position check); a destroyed bed makes it respawn at the spawn and report it; a zombie near the bed makes sleeping fail with the reason; in the Nether-guard case the tool refuses without touching the bed (unit and integration only: the e2e server has no Nether)
- **Exit criteria:** "set your spawn at this bed" makes the bot respawn there after a death; at night "go to sleep" puts the bot to bed, and it tells you exactly what else is needed for the night to pass; it never uses a bed in the Nether or the End.

### Phase 21: Signs (½ session)

Place a sign with text where the player says, and take one down again. Signs are how a player labels a chest, marks a farm, or names a room, and the bot only ever labels things in its own memory (`label_container`, `set_landmark`) with nothing visible in the world.

- Branch: `feature/signs`. Standing-sign and wall-sign placement is a client of `Placer.placeAgainst`; the target uses the `LookTarget` port with the hit face added in Phase 16 (dug rooms).
- **Tools:**
  - `place_sign`: `text` (a string that is wrapped into lines, or `lines` with up to 4) and a target: **the block the player is looking at** (the default, on the face they look at), or `at` and `face`, or `beside` a registered container by its label (the sign goes on a free side of the chest with the label as the default text). Options: `wood` (default: the sign type the bot carries, else oak), `side` (`front`, `back`), and `facing` for a standing sign (default: towards the player).
  - `edit_sign`: replace the text of a sign that is not waxed (target as above); a waxed sign is refused with the reason.
  - `remove_sign`: take down the sign the player looks at, or at `at`, or the one whose text matches within a radius; the sign is broken and picked up. It never removes a sign that was not named: there is no "remove all signs".
  - `read_signs`: the text of the signs within a radius (front and back), nearest first, so the agent can read what players wrote.
- **Rules.**
  - **Text:** up to 4 lines of 15 characters, checked at the boundary (`text_too_long` says how to split it); no colour or glow in this phase.
  - **Placement:** a wall sign on a horizontal face, a standing sign on the top face of a block (rotation from `facing`); the reference block must be solid, and never in water or lava, in a protected area, or over a spot where the bot would trample farmland. A sign is one block: `blocked` when the cell is taken.
  - **Sign items:** any `*_sign` (oak, spruce, and so on) from the inventory or storage, or crafted from planks and sticks (3 signs per craft, `CraftingSupplies`); hanging signs are left out of this phase.
  - **Editing is a separate step in 1.21:** the server opens the editor when the sign is placed, so the text is sent with the sign-update packet right after placing and read back to confirm it took; a failed write leaves the sign and reports it.
  - **Whose signs:** `SignRegistry` (persisted per world, like the container index) remembers the signs the bot placed (position, text, when). The bot removes or edits its own signs on the player's request; it removes **a player's sign only when the player points at it or names its position** (or a matching text) in that request, never on its own or in bulk, and a protected area's signs are left alone.
- **Tests:**
  - unit: text validation and wrapping (line and length limits, blank lines, an over-long word), sign item choice and crafting, wall versus standing placement from the face, rotation from `facing`, refusals (taken cell, water, lava, protected area, non-solid reference), edit refusals (waxed), removal only of a named target and never in bulk, `SignRegistry`, and `beside` a labelled container
  - integration: `place_sign`, `edit_sign`, `remove_sign`, and `read_signs` through the tool layer on a stateful fake world with a fake look target; text read back; an interrupted craft
  - e2e: a sign placed on a wall and a sign on the ground (blocks and text checked through RCON `data get block`), `edit_sign` changes the text, `remove_sign` removes the sign and the item ends in the inventory, a waxed sign (made over RCON) refuses editing but can be removed on request, a protected area refuses, and `read_signs` returns what the owner bot wrote
- **Exit criteria:** "put a sign 'Iron' on this chest" (looking at the chest) hangs a wall sign with that text; "change it to 'Ores'" edits it; "take that sign down" removes exactly that sign and picks it up; "what do the signs here say?" lists their text.

### Phase 23: Leading a player (½ session)

"Come to me and lead me to the village." A standalone feature, not part of discovery: the target can be a structure the bot found, a landmark (`home`), a registered container or farm, or plain coordinates, so it is useful with or without exploration. It builds on `Navigator`, the player lookup, `Gaze`, and chat.

- Branch: `feature/lead-player`. A `LeadPlayerSkill` (`lead_player`) in the movement skills; no engine and no new port beyond a way to face a player (the `Gaze` port already does).
- **Tool `lead_player`:** `target` (a landmark name, a known structure, or `x`, `y`, `z`), `lead_distance` (blocks, default 8, 5 to 16), `arrive_within` (default 8), and `for_player` (default the owner). The reply says what it is leading to and where.
- **The rule: the bot never gets farther from the player than `lead_distance`, and only advances when the player is close.** One loop, about twice a second:
  1. **Join.** If the bot is farther than `lead_distance` from the player, it first comes to the player (so "come to me and lead me" is a single request).
  2. **Lead.** While the player is within `resume_distance` (60% of `lead_distance`, 5 blocks by default), the bot walks the route to the target in short legs (a few blocks each, so it can stop at any moment), on the safe movement profile: it never digs or builds and avoids lava, and it prefers walkable ground, so a player can follow without special moves.
  3. **Wait.** When the distance reaches `lead_distance`, the bot stops and **turns to face the player**, and every 10 seconds or so says in chat that they should follow ("Follow me to the village"). It starts again only when the player has come back within `resume_distance`, so it does not jitter at the threshold.
  4. **The player goes elsewhere.** When the bot is waiting and the player walks away from it, the bot **goes towards the player** until the distance is under the limit again, and keeps calling them to follow. It never leaves them behind, and it does not wander ahead alone.
  5. **Arrive.** Within `arrive_within` blocks of the target it stops, says where they are ("We are at the village, x, y, z"), and the task ends with success.
- **Edge cases and safety.**
  - Player out of view or far away for about a minute: the bot stops and asks where they went (`player_lost`); after a long time of not following (about 10 minutes) the task ends (`player_not_following`).
  - Bot and target in different dimensions, or the player in another dimension: refused at the start with the reason.
  - The survival reflexes act as always and pause the task; after fleeing the task is not resumed on its own and the agent asks the player. The fixed `stop` command and `cancel_task` end it. A target that cannot be reached ends the task as `unreachable`.
  - Chat lines are throttled (one call per 10 seconds, one arrival line), so the bot never spams.
- **Tests:**
  - unit: the state machine over a fake clock, fake player positions, and a fake `Navigator` (join, lead, wait at the limit, resume at 60%, going elsewhere brings the bot back under the limit, call frequency, arrival, player lost, not following, dimension mismatch, abort, unreachable), and distance and threshold maths at the edges of the ranges
  - integration: `lead_player` through the tool layer on a stateful fake world with a scripted player who follows, lags, and walks off: the bot ends at the target, waits and calls when lagged, and follows a wandering player
  - e2e: on flat ground the owner bot follows the bot to a target 40 blocks away (both end near it, and the chat calls stayed within the limit); when the owner walks perpendicular the bot stays within `lead_distance` of the owner and does not reach the target; a `stop` ends the task
- **Exit criteria:** "come to me and lead me to the village" brings the bot to the player and then to the village, waiting and calling whenever the player falls behind, following the player if they wander, and saying when they have arrived.

### Phase 24: Autonomy, the bot's own will (2.5 sessions)

A switch that turns the bot from a helper that waits for orders into something closer to a real player: it decides for itself what to do next (gather, craft, build, dig, farm, look after and extend the home) and keeps going, while the player can still talk to it and stop it at any moment. **The agent is the brain that writes the intentions; the bot's own code is the body that carries them out.** The agent generates a *will* and attaches it to the bot; the autonomy engine then works through it with no agent round trip per step, like `LowFoodResponder` already does for food, so it also costs no model usage while it runs.

- **Two branches:** `feature/autonomy-engine` (the will, the engine, the switch, the needs, the limits, the log, the tools; about 1.5 sessions) and `feature/autonomy-goals` (the goal kinds that turn wishes into tasks; about 1). Every earlier skill is a tool the engine can use, which is why this comes late.
- **Who decides what.** Priorities from top to bottom: **reflexes** (staying alive, unchanged), **the player's instructions** (anything the owner says or asks always wins), **needs** (food, tools, a full inventory, light, night), **the will's goals**, **idle** (nothing to do: rest, report, ask the agent for more). Autonomy never overrides a reflex and never runs while a player's instruction is being carried out.
- **The will** (`WillStore`, persisted per world, `ProfileScoped` like the other state, versioned JSON): written by the agent through tools, in numbers and names the engine can use:
  - `identity`: a short character and style for the bot's chat lines (how it talks, how often it reports);
  - `home`: the landmark the bot lives around and works from;
  - `goals`: each has an `id`, a `kind` (from the catalog below), `params`, a `priority`, and an optional stop condition (`until`: a stock level such as 64 logs in the chest, a count, a size, a date, or never) and repeat (`every`);
  - `boundaries`: what the bot must never do while acting on its own (see the limits below), on top of protected areas, standing instructions, and every policy that already exists.
- **Goal kinds** (each a `GoalStrategy`, a new one is a new class, registered in the composition root; a strategy turns a goal and the current state into **one concrete task** through the tool registry, so everything it does is an ordinary, cancellable, journalled task): `stock` (keep an item at a level in a chest: gather, hunt, smelt, or craft what is needed), `farm` (`tend_farm` on a group, replant, breed, collect eggs), `build` (a blueprint at a plot, with materials fetched or gathered), `improve_home` (a list of blueprints and rooms the agent wrote, done in order), `excavate` (a dig from the will), `explore` (find a kind of structure), `tidy` (deposit by the storage rules), and `rest` (sleep at night, stand in shelter). A goal that cannot be done because of a typed failure gets the usual answer: `missing_materials` adds a gather step, `no_suitable_tool` a craft step, `inventory_full` follows the storage policy, and anything else marks the goal `blocked` with the reason so the agent can change the will.
- **The engine** (`AutonomyEngine`, a small state machine using `Clock`, `Random` for seeded tie-breaks, and `Scheduler`; no Mineflayer): `off`, `watching` (nothing to do yet), `acting` (one task running), `waiting_for_approval` (only with `require_approval`), `paused_by_player` (the owner spoke or said `stop`), `paused_by_reflex`, and `blocked` (every goal is blocked or done). It picks the goal with the highest priority that is due and not blocked, launches it, records the result, and repeats. **When the will runs dry or every goal is blocked, the engine tells the agent** (an `autonomy_needs_will` event in `wait_for_chat`) and idles or rests until the agent extends the will. **Without an attached agent the bot only repeats and maintains what the will says** (stock levels, farms, upkeep); inventing new projects needs the agent.
- **The switch, and approval as a second, separate switch.** `set_autonomy` takes two independent settings:
  - **`enabled`**: **off by default, and off after every restart**. Turned on by the agent, or by fixed commands in code that never wait for the agent (`ChatCommand`s, like `stop`): **`autonomy on`** and **`autonomy off`** from the owner's chat. The owner's `stop` cancels the running task and **pauses** autonomy (not off) until they say to go on.
  - **`require_approval`**: **off by default**. With it off, the bot **does not wait for the owner's approval**: it acts on its will as soon as it is enabled, and a will (or a new goal) that the agent writes takes effect at once, visible in `get_will`, the session briefing, and the log, and changeable or removable by the owner at any time through the agent. With it on, the bot says in chat what it wants to do next and waits for a yes (`needs_decision`, answered with `resume_task`), and new or changed goals from the agent wait for the owner's yes before they count. It can be limited to some goal kinds (`approval_for`, for example `excavate` and `build`) and is switched by the owner's chat (`autonomy approval on` and `off`) as well as by the agent.
- **The player always comes first.** When the owner speaks, the engine finishes or cleanly aborts the current step at the next safe point and hands over to the agent; it goes back to its own will by itself after a quiet time: **default 4 minutes** without a message from the owner (`resume_after_minutes`, 1 to 30, in `set_autonomy` and the will's `boundaries`; 3 to 5 is the intended range), or at once when told "carry on", and never while a player's task is still running. The bot chats like a player, not like a log: one short line when it starts something bigger, when it finishes, or when it is stuck, at most one per minute, in the voice of `identity`.
- **Limits** (`Governor`, checked before every task and while it runs; the defaults can be changed in `boundaries` and by the player): stay within a radius of home (default 200 blocks); do not change dimension or teleport; never break or build in protected areas or inside player-built structures (all existing rules); no work at night away from shelter unless the goal needs it; a maximum length per task and a maximum number of tasks per hour; do not spend the last food and torches; do not take from or empty protected containers; **a kill switch: after 2 deaths in an hour, or 5 blocked goals in a row, autonomy turns itself off and tells the owner** (a bot that keeps dying should not keep going). Anything that needs a decision the will does not cover (dig deeper than allowed, a danger it does not know) becomes a `needs_decision` event, never a guess.
- **Visible and reviewable.** `AutonomyLog` (bounded, persisted) records every decision with the reason ("stock: logs 12 of 64, gathering 30"), the task it started, and the result; the session briefing shows whether autonomy is on and whether approval is required, the current goal, the last decisions, and blocked goals. `get_autonomy_log` lets the agent review and revise the will, and nothing happens silently.
- **Tools:** `set_autonomy` (`enabled`, `require_approval`, `approval_for`, `resume_after_minutes`), `get_autonomy_status`, `get_will`, `set_will`, `add_goal`, `update_goal`, `remove_goal`, `list_goal_kinds` (each kind with its parameter schema, so the agent writes valid goals), `get_autonomy_log`. All validated with zod at the boundary; a will with an unknown kind or bad parameters is refused with the reasons.
- **Safety and the operator.** Autonomy is a switch the operator owns: it is **off after every start**, and an unattended bot acting in the operator's real world is exactly what the live-testing rule guards against, so turning it on in a real LAN world is announced in chat and needs the owner's own command or a clear yes; the agent asks before switching it on. Approval per action is a different thing and is off by default (see the switch). Every action is an existing tool with its own safety checks, so autonomy adds decisions, not new ways to change the world.
- **Tests:**
  - unit: the state machine over a fake clock, fake random, and a fake task launcher (each transition, priority order of reflex, player, needs, goals, idle; a chat message pauses and the quiet time (4 minutes by default, changeable) resumes it, and a new message restarts the count; `stop` pauses; abort; with `require_approval` off nothing waits, with it on the engine waits for the answer and a `no` skips the goal, and `approval_for` limits it to some kinds), the `Governor` (radius, dimension, protected areas, night, hourly cap, food reserve, the kill switch on deaths and blocked goals), `WillStore` (validation, persistence, versioning, a corrupt file falling back), each `GoalStrategy` (goal and state give the expected task; typed failures give the expected follow-up; stop conditions and repeats), the log bounds, and the chat throttle
  - integration: the real engine, registry, and tools through the MCP layer on a stateful fake world: a will with `stock` and `farm` goals runs to its stop conditions, a player instruction preempts and the engine resumes, `set_autonomy off` cancels cleanly, a blocked will raises `autonomy_needs_will`, approval on and off (a will change from the agent is held until approved only when it is on), and a restart comes back with autonomy off
  - e2e: in the Docker server, a will "keep 20 oak logs in the chest" with autonomy on: the bot gathers, deposits, and stops at 20 (checked through RCON); the owner bot's chat message pauses it and `autonomy off` stops it; a boundary radius is respected; two deaths switch it off
- **Exit criteria:** with a will written by the agent ("keep the chest stocked with logs and food, tend the farm every day, and build these rooms next to the house"), turning autonomy on makes the bot work through it on its own, without waiting for approval unless `require_approval` is switched on, talking a little like a player, pausing whenever the owner speaks, stopping at once on `stop` or `autonomy off`, and telling the agent when it runs out of things to do; the log shows why it did each thing.

## Testing strategy

Three automated tiers. Unit and integration run offline with no Minecraft and make up `npm test`. E2E runs against a real headless Minecraft server in Docker. Before a phase is merged into `development`, its unit and integration tests and **its own e2e tests** must pass; the complete e2e suite (all phases) is run once, at the final gate after all primary phases.

| Tier | Scope | Real parts | Fake parts | Location |
|---|---|---|---|---|
| Unit | One class or function | the unit under test | all its ports, `Clock`, `Random` | `test/unit/` (mirrors `src/`) |
| Integration | Several real modules wired together | MCP server + client (SDK in-memory transport), `ToolRegistry`, `TaskManager`, `AgentInbox`, reflex engine, skills, `WorldKnowledgeStore` on a temp dir, `createApp()` wiring | the outer ports (`Connection`, `Navigator`, scanners, `Digger`, `Placer`, ...), usually as a stateful fake world | `test/integration/` |
| E2E | The whole app against a real server | everything: real `createApp()`, real Mineflayer adapters, real Minecraft 1.21.1 server (Paper in Docker) | nothing (the world is prepared and inspected through RCON; a second bot or RCON simulates the player) | `test/e2e/` |

Rules:

- All code is written to be testable: constructor injection, no global state, no direct `Date.now()`/`Math.random()`/`setTimeout` outside injected `Clock`/`Random`, no Mineflayer imports outside thin adapters.
- Adapters in `src/bot/` are unit-tested against a small stub of the Mineflayer API (event emitter plus the few methods used).
- Every bug found in the game gets a regression test at the lowest tier that reproduces it.
- Coverage gate: 90% lines/branches on `src/` (excluding only the trivial `src/index.ts` entry), enforced from Phase 1 on unit and integration tests. E2E tests do not count toward coverage.
- E2E scope: a small smoke-level set per phase, not exhaustive. Behavior details belong in unit and integration tests; e2e proves the real bot works against a real server.
- E2E prerequisites: Docker running locally. One server container per run, scenarios isolated by area and reset through RCON.
- E2E tests are excluded from `npm test`, so the fast loop stays fast. They are grouped per feature (`test/e2e/<feature>/`): while working on a phase you run only its own feature group, never the accumulated earlier groups. The complete suite (`test:e2e:all`) runs at the final gate in the hardening phase and before any `release/*` merge into `main`. Unit and integration tests are cheap, so they are always run in full.

## Git workflow

Git Flow, with `main` as production and `development` as the integration branch.

- `main`: production only. Updated by release merges, tagged `vX.Y.Z`.
- `development`: integration branch. All work starts here and returns here.
- `feature/<name>`: one per phase or feature, created from `development` (for example `feature/movement-perception`; names describe the feature and never contain phase numbers), merged back into `development` with `--no-ff` once tests pass and the phase's manual check is done.
- `release/<version>`: cut from `development`, merged into `main` (tagged) and back into `development`. The complete test suite, including `test:e2e:all`, must be green on the release branch.
- `hotfix/<name>`: cut from `main` for urgent production fixes, merged into `main` and `development`.
- Conventional Commit messages (`feat:`, `fix:`, `test:`, `docs:`, `refactor:`, `chore:`).
- No direct commits to `main` or `development` (apart from the one-time repository bootstrap in Phase 0).
- Merging into `development` happens after your approval of the phase; merging into `main` only on your explicit request.

## Manual in-game check (used at the end of each phase)

This is a human verification step with the real game client, in addition to the automated e2e suite. It also covers what Docker cannot: your actual LAN world and the in-game chat UX.

1. Start Minecraft 1.21.1, open the world to LAN, note the port.
2. Start the MCP client, `connect` with the port; the bot appears.
3. Run the phase's exit-criteria scenarios via in-game chat.
4. Check stderr logs for errors and unexpected stdout output.
5. Verify `stop` interrupts within about a second.
